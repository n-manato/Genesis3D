# 08 — game_avatar：固定トポロジ方式

写真1枚から**ゲームキャラクター**を作る。超リアル路線（`realistic_jrpg`）からの方向転換で、
出荷されているゲームの作り方を調べ直したうえでの設計。

前提が1行で変わる:

> **写真から作るのはメッシュではない。パラメータである。メッシュは常に同じ一体を使い回す。**

---

## 1. なぜ変えるか

`docs/05-measurements.md` に残っている未解決項目は、別々の不具合に見えて原因が1つしかない。

| 症状 | 実測 | 原因 |
|---|---|---|
| 指が動かない | §38 | 生成メッシュの手が割れていない塊で、指の骨40本がメッシュ外に浮く |
| 肩・胸で破断する | §37 | 167本中130本がメッシュ外に浮き、heat map が解けない |
| spring bone が無い | §36 | 毎回ちがう髪に揺れ骨を自動で入れられない |
| 髪が焼き込みのまま | §46, §48 | DiffLocks のヘアカード化が全身の距離で「濡れた藁」になり撤回 |

すべて **「毎回メッシュが違う」** から出ている。TRELLIS が写真ごとに新しいトポロジを吐き、
そこへリグ・表情・揺れものを後から当てにいく構造そのものが原因になっている。

固定テンプレート方式では、リグ・ウェイト・表情・spring bone・MToon を**一度だけ手で仕上げる**。
以降どの写真を入れても品質はその一体の品質で決まり、上の4項目は構造的に消える。

### 掘るべきは NetEase Fuxi の4本

出荷されたゲームの中身が論文とコードで公開されている唯一の系統。
『逆水寒』に載って100万回以上使われている。読む順序がそのまま実装の順序になる。

## 3. 共通構造 — 6つの層

| 層 | 内容 | 出典 |
|---|---|---|
| L1 取得 | 入力の質を実行時に強制する。Roblox は**その場撮りの自撮りしか受けない**。NBA 2K はアプリが姿勢を指示する（目線の高さ・約45cm・首を45°まで・正面光・逆光不可・無地背景） | Roblox / NBA 2K |
| L2 **2D様式化** | 実写からいきなり様式化パラメータを解くと**ドメイン差で解が壊れる**。先に2Dの画像として様式化し、それを目標にして合わせにいく。Roblox の「2Dプレビューを承認させてから3D」も同じ構造 | AgileAvatar |
| L3 パラメータ推定 | **imitator**（微分可能な代役）＋**translator**（一発推定）。損失は identity（顔認識特徴のコサイン距離）と content（顔パーシングの画素一致）の2本立て。離散は softmax でグループ正規化 | F2P |
| L4 幾何への反映 | (a) パラメータ駆動（ボーン駆動の顔モデル）／ (b) **形状転写**（68点対応の RBF）。どちらも**トポロジ・UV・ボーン・ウェイト・ブレンドシェイプは変わらない** | F2P / MeInGame |
| L5 テクスチャ | 肌領域検出 → 平均肌色をテンプレへ → 変形後メッシュに沿ってUVへ展開 → Poisson 合成 → 非肌領域除去 → **左右対称性で隠れた側を埋める** | MeInGame §3.1 |
| L6 編集・審査 | 自動生成は初期値。ZEPETO も Roblox も Naraka も、必ず手で直す導線を置く。**「一発で完璧」を目指した実装は無かった** | 全社 |

## 4. ArcFace はここから先は目標にならない

§42 の「ICT の幾何に差し替えたら ArcFace 0.708 → 0.394」は、超リアル路線では明確な失敗だった。
ゲームキャラ路線では **そもそも下がるのが正しい**。

ArcFace は実写どうしの照合器で、意図的にデフォルメされた顔を「別人」と判定するのが本来の挙動である。
同一人物の実写どうしで 0.79 という手元の基準は、様式化した瞬間に上限として意味を失う。

代替の測り方は3つ:

1. **様式化画像との照合** — L2 で作った2D様式化画像を基準にして、そのレンダとの顔特徴距離を測る。実写ではなく「目標の絵」と比べる
2. **content loss 相当** — 顔パーシングの画素一致。目鼻口が同じ位置に同じ大きさで載っているか。デフォルメしても比率は保たれるので生き残る
3. **人手の選好比較** — AgileAvatar が主要指標に据えているもの

> §42 は失敗の記録ではなく、路線変更の根拠だった。
> 「幾何を本人に寄せると同一性が上がる」のはリアル路線の法則で、
> ゲームキャラでは**比率だけ本人・造形はテンプレート**が正解になる。

## 6. 設計上の要 — Blender を経由しない

`blender/vrm_finalize.py` の冒頭が明言しているとおり、
**VRM の再インポート・再エクスポートはテクスチャを再エンコードして個体を別物にしうる**。
同ファイルはそのために Blender を経由せず glTF の JSON/BIN を直接書き換えている。

**RBF 変形は POSITION accessor の書き換えでしかない。まったく同じ手が使える。**

これにより spring bone・MToon・node constraint・テクスチャが
**「保たれる」のではなく「触られない」** — VRMアドオンの往復で壊れるリスクが構造的に消える。

再利用する既存ヘルパ（すべて `blender/vrm_finalize.py` 内）:

| 関数 | 行 | 用途 |
|---|---|---|
| `read_glb` / `write_glb` | :57 / :76 | GLB の分解・再構成 |
| `gc_accessors` | :234 | 未参照 accessor の除去と番号振り直し |
| `sparsify_morphs` | :283 | **sparse accessor の読み書き**（モーフ差分の読み出しに必要） |
| `repack` | :366 | 参照されている bufferView だけ詰め直す |

Blender の出番は**テクスチャのベイクとレンダのみ**に縮む。

### spring bone を残すのは仕様の後退ではない

`vrm_finalize.py` が `drop_spring_bones` を持つ理由は
「衣服が体のシルエットに焼き込まれていて、揺らすべき別メッシュが存在しない」から（同 :17-19）。

テンプレートを保つ `game_avatar` では **Tops メッシュが実在するので22本の spring bone はそのまま正しい**。
前提が変わることによる正常化であって、検査を緩めるわけではない。

## 7. パイプライン

```
input.png
  │
  ├─[1] 前処理           GPU0   RMBG-2.0（既存の工程1を流用）
  │
  ├─[2] 2D様式化         GPU1   RealVisXL V5.0 + ControlNet     ← M2
  │                             実写を目標スタイルの絵に変換する
  │
  ├─[3] 顔の同定         CPU    insightface antelopev2 で68点3Dランドマーク
  │                             → ICT-FaceKit 識別空間（100次元PCA）を解く
  │
  ├─[4] 形状転写         CPU    RBF（MeInGame §3.3）
  │                             68点対応 → 放射基底補間でテンプレ全頂点を変位
  │                             **glTF 直接編集。Blender を通さない**
  │
  ├─[5] デフォルメ       CPU    識別変位の誇張係数・スタイル固有の再マップ  ← M2
  │
  ├─[6] テクスチャ       GPU0   様式化画像をUVへ展開 → Poisson 合成
  │                             → 非肌領域除去 → 左右対称で補完
  │
  ├─[7] 髪・色           CPU    髪型はテンプレ N 個からの**分類**          ← M2
  │                             髪色・肌色・目色は連続値で回帰
  │
  ├─[8] 組み立て         CPU    テンプレのリグをそのまま使う。転写しない
  │                             vrm_finalize は条件分岐（springBone/MToon を残す）
  │
  └─[9] 検証・QA         CPU    既存の工程10・11をそのまま流用
```

**TRELLIS も CharacterGen も MICA も使わない。**

## 8. マイルストーン

### M1 — 様式化なしで VRM まで通す

工程1・3・4・6・8・9 のみ。実写のまま固定トポロジへ転写して VRM まで出す。

**確認したいのは見た目ではなく、`pose_check` で
「指が動く・肩が割れない・spring bone が生きている」が成立するかどうか。**
成立すれば方式選択はそこで決着する。

### M2 — 様式化と髪を入れる

工程2・5・7 を追加。「ゲームキャラに見えるか」はここで初めて評価対象になる。
評価は**様式化画像を基準に測り直す**。

### M3 — パラメータ空間へ

テンプレートに捏脸モーフ群を用意し、識別変位を最小二乗でその空間へ射影する。
出力が常にそのゲームの顔の範囲に収まり、ユーザーがスライダーで後から直せるようになる。
translator（顔認識特徴 → パラメータのMLP一発推定）の学習はこの段階。

### 10.2 モーフ差分の式 — `d` を足し忘れると壊れる

当初 `d' = f(x+d) − f(x)` と書いたが**誤り**。glTF が持つのは基準形状からの差分なので、

    d' = (x + d + f(x+d)) − (x + f(x)) = d + f(x+d) − f(x)

`d` を落とすと、純粋な相似変換ですら差分が `A·d` ではなく `(A−I)·d` になる。
相似変換の合成テストがこれを捕まえた。ヤコビアンによる一次近似は不要で、
f を2回評価するだけでよい。

### 10.3 アンカー点は任意ではなく必須

鼻先1点だけを 12mm 前に出す局所変形で、鼻先からの距離ごとの変位を測った。

VRoid テンプレート（頭部のみ・25k頂点）:

| | 鼻先(<2cm) | 中間(5〜20cm) | 遠方(>40cm) |
|---|---|---|---|
| アンカー無し | 12.00 mm | 0.76 mm | **1.200 mm** |
| アンカー200点 | 12.00 mm | 0.70 mm | **0.045 mm** |

Rocketbox（全身 1.824m）では**桁が変わる**。多項式項の外挿が足まで届くため:

| | 鼻先(<2cm) | 中間(5〜20cm) | 遠方(>40cm) |
|---|---|---|---|
| アンカー無し | 12.00 mm | 2.06 mm | **13.113 mm** |
| アンカー200点 | 12.00 mm | 1.07 mm | **0.134 mm** |

98分の1。**全身テンプレートではアンカーの重要度が上がる。**
アンカーは `preprocessing/template_anchors.py` が顔の下端から 8cm 下を境に、
最遠点サンプリングで打つ（偏るとその周辺だけ強く拘束されて歪む）。

phi(r)=r ＋ 一次多項式は**大域的な台**を持つので、鼻を動かすと足が 1.2mm 動く。
首より下（y < 1.30）に最遠点サンプリングで**ゼロ変位のアンカーを200点**打つと
遠方が 27分の1 に落ち、意図した 12.00mm は変わらない。

`configs/templates/<id>/anchors.json` は「あると良いもの」ではなく、
**これが無いと足が動く**。

### 10.4 KEHAI について確認した3点

いずれもソースを読んで裏を取った。

**(a) KEHAI は VRM の expression を読まない。** `vrm-expression.ts:558` と
`vrm-viewer.tsx:5117` が「`vrm.update()` の後に走って expressionManager を上書きする」と
明記している。語彙の判定は `vrm-expression.ts:343` の
`profile = dict["まばたき"] != null ? "pmx" : "arkit"` で、**生のモーフ名だけ**を見る。

→ テンプレートの `Fcl_*` 命名は PMX でも ARKit でもないので arkit と判定され、
探しに行った `eyeBlinkLeft` が無くて何も動かない。実測:

```
sample.vrm   語彙 arkit   ✗ まばたき   ✗ 口パク
             注意: VRM expression プリセットが14個 結線されているが KEHAI は読まない
```

**→ ARKit 命名のモーフ併載は M1 の任意項目ではなく必須。**
最低限 `eyeBlinkLeft` / `eyeBlinkRight` / `jawOpen` の3つは、テンプレート自身の
`Fcl_EYE_Close_L` / `Fcl_EYE_Close_R` / `Fcl_MTH_A` への**別名として張れば0バイトで済む**
（glTF は accessor の使い回しを許す）。VRoid の目は人間と形が違うので、
まばたきは ICT から転写するより**テンプレートが手で作った物を使うほうが確実に閉じる**。

**(b) `scripts/check_kehai_model.py` が VRM を誤判定していた。** Mixamo のノード名を
探すので、humanBones を54本持つ健全な VRM が「必須16本すべて欠落」と出ていた。
`.vrm` は three-vrm が `VRMC_vrm.humanoid` を読み、Mixamo 名を見る `glb-humanoid.ts` は
`.glb` 専用の経路。**修正済み** — `is_vrm` で分岐し、語彙・spring・MToon・
結線済みプリセット数も報告するようにした。

**(c) `blender/project_face.py:283` の `materials[0]`。** マテリアルスロットの
0番を決め打ちしている。テンプレートの `Face` は7プリミティブ＝7スロットで、
**0番は `FaceMouth_00_FACE`** — 顔ではなく口に写真を合成する。
`--only-materials` では救われない（`wanted()` はオブジェクト単位で照合するため）。
例外を投げずに間違ったテクスチャを出すので、テクスチャ工程の前に直す必要がある。

## 10.7 写真から形状まで通した（2026-09-02）

工程1〜4が繋がった。**写真1枚 → 68点 → ICT識別係数 → 対応点 → 変形テンプレート。**
TRELLIS も MICA も使っていない。

```
preprocessing/ict_photo_fit.py     写真 → α（識別100次元）＋ β（表情53次元、捨てる）
preprocessing/deform_params.py     α → テンプレートの対応点（68 + アンカー200）
preprocessing/shape_transfer.py    対応点 → 変形した GLB
```

誇張係数の掃引: `assets/templates/rocketbox/exaggeration_sweep.png`。
**k=1.0 が自然、1.5 まで実用、2.0 から眉と口が強張り始める。** 既定は 1.0。

### 表情が同一性に焼き付く問題は実在した

元写真が笑って口を開けているため、素直に α を解くと**テンプレートの口が開いた**。
k=2.5 まで誇張すると歯が見えるほどになる。PokerFace-GAN (2020) が名指しで解いた
問題そのもの（§2）。

ICT は識別100本とは別に**表情53本**を持っているので、

    V = V_mean + Σ α_k · Id_k + Σ β_j · Expr_j

として同時に解き、**β を捨てて α だけを渡す**。口は閉じた。線形なので学習も追加の
反復も要らない。分離された β の上位は `cheekPuff_L/R` `mouthFunnel` `noseSneer_R` で、
笑った写真として妥当な内訳になっている。

### リッジの正規化で二度間違えた

**(1) 成分ごとの σ で頭打ちにしたら係数が動かなくなった。** ICT の
`identity000..099` は「1本が係数1.0で1モード分」なので、基底ノルムで正規化すると
モード0が突出しているぶん他が潰れる。**100個中89個が頭打ち**になった。一律 ±3 が正しい。

**(2) リッジのスケールを識別と表情の共通 trace から取ったら識別が潰れた。**
表情基底の変位が識別より大きいので trace が表情に支配され、識別側が過剰に抑えられる。
実測で **alpha_norm 15.2 → 2.25**、再投影誤差も 2.90px → 5.44px と悪化した。
**ブロックごとに自身の対角平均で割る。**

`EXPR_RIDGE` の掃引（ブロック正規化後、`subject_face_downtown_1200.jpg`）:

| expr_ridge | RMS px | alpha_norm | beta_norm | 上位の表情 |
|---|---|---|---|---|
| 0.1 | 5.76 | 10.52 | 2.01 | cheekPuff_R/L, mouthStretch_L |
| 0.3 | 4.64 | 11.40 | 1.25 | cheekPuff_L/R, mouthRollUpper |
| **1.0** | **4.30** | **12.24** | **0.58** | cheekPuff_L/R, mouthFunnel |
| 3.0 | 4.54 | 12.76 | 0.31 | jawOpen, mouthFunnel |
| 10.0 | 4.22 | 13.40 | 0.19 | jawOpen, mouthFunnel |
| 表情なし | 2.90 | 15.16 | — | （笑いが同一性に焼き付く） |

**再投影誤差だけで選ぶと「表情なし」が最良に見えるが、それは笑いを同一性として
説明しているだけ。** 合否は誤差ではなく、口が開くかどうかで決めた。既定は 1.0。

### 左右対称化

k を上げると眉と口が片側だけ吊り上がった。写真の頭がわずかに傾いていて、
その非対称が同一性として入っている。**顔の同一性はほぼ左右対称**なので、
68点の左右対応で変位を鏡像平均する（`deform_params.symmetrize`）。
落ちた非対称成分は 1.037mm だった。これで k=2.0 まで歪まなくなった。

## 10.8 テクスチャ工程 — 写真の顔が乗った（2026-09-02）

工程6が通り、**写真の同一性が実際にテンプレートへ移った**。
`assets/templates/rocketbox/texture_first_pass.png`（左から 元写真 / 素体 / 形状のみ / 形状＋テクスチャ）。

経路は既存のものをそのまま使う:

```
blender/project_face.py --emit-align-render      整列用の正面レンダ
preprocessing/face_projection.py                 写真を ArcFace 5点で整列
blender/project_face.py --face-material head     変形後メッシュへ投影して焼く
```

### 三つ潰した

**(1) Metallic = 1.0（最重要）。** Rocketbox の FBX は PBR の情報を持たないので、
glTF 化すると `metallicFactor` が省略され、**仕様の既定値 1.0 = 完全な金属**として
解釈される。金属には拡散成分が無いので **Cycles の DIFFUSE bake が全面黒**になった
（焼いた画像の平均RGBが [0,0,0]）。

これは焼き込みだけの問題ではない。**肌と布のアバターが金属として登録されている**ので、
KEHAI のような PBR レンダラで正しい環境光を当てても誤って映る。
`scripts/prepare_rocketbox.py` がテンプレート生成時に 0 にする。

EEVEE の簡易プレビューではそれらしく見えてしまい、**レンダで確認していると気づけない**。
気づいたのは bake が黒になったからで、順序が逆なら見逃していた。

**(2) 焼き方を EMIT に変えた。** DIFFUSE bake は BSDF の設定に結果が左右される
（上記のとおり Metallic で消える）。ベースカラーを一時的に Emission へ繋いで EMIT で
焼けば、シェーダの状態に依存しない。`blender/project_face.py` の
`_as_emission` / `_restore_surfaces`。

**(3) `Icosphere` が毎回生える。** Blender 4.2 の glTF インポータは読み込みのたびに
42頂点の `Icosphere` を作る（`subject_a.glb` でも Rocketbox でも再現）。
マテリアルを持たないのでマテリアル選択で落ちる。投影対象からも書き出しからも外した。

### 外した仮説（記録）

`Color Attribute` ノードの `layer_name` が空で、EEVEE は落ちないが Cycles は黒を返す
——という仮説を立てて補修コードを入れたが、**補修しても黒のままだった**ので誤りと判明。
`layer_name` が空なのは事実だが（Blender 4.2 の glTF インポータがそう作る）、
Cycles はアクティブな色属性へ正しくフォールバックしている。コードは削除した。

切り分けは「定数の赤を焼く → それでも黒」で、マテリアル評価ではないと分かり、
「EMIT なら焼ける → DIFFUSE だけ黒」で拡散成分の不在に辿り着いた。

### 残っている問題

**同一性は移ったが、まだ MeInGame §3.1 の後半が入っていない。**

- **非肌領域が落ちていない** — 写真の髪と赤いジャケットがそのまま焼かれ、
  額から生え際、首に赤い斑が乗っている
- **テンプレートの肌と繋がっていない** — 顔だけ本人の肌色で、首から下は素体のまま
- **左右の補完が無い** — 隠れた側が埋まらない
- **写真の表情がテクスチャに焼き付く** — 形状側は §10.7 で分離したが、
  テクスチャは笑ったままになる。これは MeInGame も同じで、
  L5 の肌合成では解けない（表情の無い写真を使うか、2D側で処理するしかない）

次は `texture_processing/skin_blend.py`（Poisson 合成・非肌除去・対称補完）。

| **fingers** | **94.2mm** | **87.6mm** |

**指が動く。** 生成メッシュでは指の骨40本がメッシュ外に浮いて動かせなかった（§38）。
テンプレートの手塗りウェイトがそのまま入っているので成立する。

`mesh_report` はテンプレート素体と**完全に一致**（`duplicate_vertex_candidates` が
1238→1231 だけ。これは閾値ヒューリスティックで、変形で近接頂点がわずかに離れたもの）。
glTF 頂点は **5563 でテンプレートと同一**。

### 焼いた画像は「無傷の変形後 GLB」へ注入する

`project_face.py` は Blender の import/export を通るので、**頂点が 5563 → 5569 に増える**。
テクスチャは UV 空間の画像なので、焼いた画像だけを取り出して変形後 GLB に注入すれば
往復を回避できる。投影後の GLB は捨てる。

これで**ジオメトリは一度も Blender を通らない**。Blender の出番は整列レンダと
焼き込みだけになった。副産物としてファイルも 25.5MB → 10.5MB に縮んだ
（往復するとテクスチャが PNG に再エンコードされる。WebP のまま注入すれば済む）。

### pose_check の判定を頂点変位に変えた

外接の変化で測っていたため、**局所の動きを取りこぼしていた**。

- 片脚だけ曲げる `legs` → もう一方の脚と腕が外接を決めて **0.0mm**
- 指を握らせる `fingers` → 男性素体は既存の外接の内側で曲がるので **0.0mm**

どちらも骨は見つかって回っているのに「変形せず」と報告される false negative だった。
頂点ごとの最大変位に変えたところ、指は **94mm / 88mm** と出た。
外接の値も `bbox_delta` として残してある。

あわせて `ALIASES` を足して Mixamo 命名（`LeftArm` / `LeftHandIndex1`）を認識させた。
VRoid 命名しか見ていなかったので、Rocketbox 由来のテンプレートでは
`bones: []` になり**リグが壊れているように見えていた**。

### 画角の余白は上下どちらにも失敗の側がある

`project_face.py --frame-material` の余白を 1.25 のままにすると、**男性素体で
顔検出が落ちた**。`head` マテリアルの帯には髪が入らないので、髪の多い個体では
顔が枠を占めすぎて SCRFD が外す。既定を 1.45 にした
（`ortho_front.py` の `MATERIAL_MARGIN = 1.35` と同じ話）。

狭いと検出が落ち、広いとテクセル密度が下がる。`--frame-margin` で調整する。

### KEHAI に登録した

`scripts/register_kehai.py` が検査 → コピー → `model_dict.json` の冪等な upsert →
`characters/<name>.yaml` の書き出しを行う。検査に落ちたら登録しない。

```bash
python3 scripts/register_kehai.py --model jobs/ga_female_001/output/avatar.glb \
    --name subject_a_game --display "Subject A（ゲーム体）" \
    --conf-uid subject_a_game_001 --persona prompts/personas/subject_a_en.txt \
    --voice VQ5VvKYXlRGiLCzb4owE
```

**`emotionMap` に注意。** `vrm-expression.ts` は語彙が arkit なら ARKIT_PRESETS で
表情を作るが、**`emotionMap` に無い感情は呼ばれない**。ARKit 52 を持つモデルに
`{"neutral": 0}` だけ書くとモーフはあるのに表情が動かない。語彙が arkit なら14感情を入れる。

### KEHAI 側の記述の誤りを直した

`subject_a_v2` は yaml と `model_dict.json` の両方で「モーフターゲットを持たない・
口パクも表情もまばたきも動かない・後から足しても本物にはならない・
しゃべらせるなら subject_a を使え」と書いていたが、**実体には ARKit 命名の

モデルが後から差し替わって記述だけ取り残されていた。`emotionMap` も
`{"neutral": 0}` のままで ARKit の表情が呼ばれない状態だったので、14感情に直した。

## 10.11 やり直しの調査 — 前回の方式は同一性を 0.32 落としていた（2026-09-03）

### held-out ArcFace で測って初めて分かった

**前回「M1 完了」と報告する前にこれを測るべきだった。** 由来写真ではなく
**別セッションの実写**を基準にした held-out 評価:

| 出力 | 顔px | vs 由来写真 | **vs tweed(別)** | **vs studio(別)** |
|---|---|---|---|---|
| 実写どうし（tweed vs studio） | — | — | — | **0.8203** ← 上限 |
| **subject_a_v2（旧パイプライン）** | **80** | 0.8368 | **0.7790** | **0.7680** |
| **game_avatar（固定テンプレート方式）** | **272** | 0.5153 | **0.4554** | **0.4469** |
| Rocketbox 素体（本人性ゼロ） | 282 | −0.0722 | −0.0751 | −0.0782 |

旧パイプラインは顔の画素数が **3.4分の1** でこの結果。§19 の「顔の画素数が効く」に
従えば条件を揃えると差はさらに開く。

**原因: 写真を誤った幾何の上に貼ると顔が歪む。** RBF は平均4.7mm しか動かしておらず、
テンプレートの頭は依然として別人の頭だった。

**§42 はこれを既に警告していた**（ICT の当て込み幾何で 0.708 → 0.375〜0.394）。
それを「指標のほうが誤り」と読み替えたのが誤りで、**その読み替えが正しかったのは
様式化を狙う場合だけ**。実写寄りに方針転換した時点で指標を戻すべきだった。

### 多視点三角測量は、この写真では機能しない

単一写真では奥行きが観測できないので、生成モデルを使わずに奥行きを得る道として
多視点三角測量を実装した（`preprocessing/multiview_landmarks.py`）。
視点を伏せて検証した結果:

**伏せた視点への再投影誤差**（顔幅で正規化。小さいほど形が正しい）

| 学習に使った視点 | → yaw+32 | → yaw−25 |
|---|---|---|
| 平均顔のまま（対照） | 0.0398 | 0.0450 |
| 正面1枚のみ | 0.0321 | 0.0261 |
| **正面2枚（奥行き情報ゼロ）** | **0.0198** | **0.0233** |
| 正面 + yaw−25 | 0.0250 | — |
| 正面 + yaw+32 | — | 0.0197 |

**奥行き情報を持たない「正面2枚」のほうが、横向きを足した場合より伏せた視点に
良く当たる。** 手持ちの横向きは顔が 64〜70px しかなく、ランドマークの誤差が
奥行きの情報を上回っている。**ノイズを足しているだけ。**

高解像度化でも救えない。§40 の実測が「**単純な拡大は同一性をほぼ完全に保つ**
（Lanczos 1.914倍で 0.9920）」＝情報は増えない、と示しており、SDXL 復元は
guidance 5.0 で「明らかに別人」（0.6115）になる。

### 多視点テクスチャも同じ理由で駄目

幾何ではなくテクスチャとして横向きを使う案も測った。整列後の実効的な顔幅が
**26px / 27px** で、レンダ側（201〜213px）に合わせると8倍に拡大される。
側面のテクスチャとして使えない。

### 結論 — 制約と手持ちの写真では顔の幾何に解が無い

「生成再構成を使わない」＋「手持ちの写真」の組み合わせでは、
**顔の幾何を本人に合わせる方法が存在しない**。同一性の上限は 0.46 前後で、
それは前回の実装で既に達成している。

残る手は幾何以外の4つ（照明を割る・表情のニュートラル化・法線ディテール・
顔領域の細分）で、これらは**「貼り付けて見える」という見た目の問題には効くが、
ArcFace はほとんど動かない**。

### 本当の解は「撮り方」— 出荷システムがそうしている

§3 の L1 に書いたとおり、**NBA 2K はアプリが撮影の姿勢を指示する**
（目線の高さ・約45cm・首を左右45°までゆっくり・正面光・逆光なし・無地背景）。
Roblox は**その場撮りの自撮りしか受け付けない**。

単一写真が不十分なことを彼らは知っていて、**入力の分布を狭めることで解いている**。
手持ちの写真は第三者の広報写真の寄せ集めで、横向きは 64px しかない。

**正面＋左右30°を高解像度（顔300px以上）で撮り直せば、三角測量は生成モデル無しで
成立する。** 元々の要望「実際に写真を撮ってアバターを作る」にも合う。

### 方針

生成再構成を解禁したうえで、**旧パイプラインも前回の実装もやっていなかった組み合わせ**にする。

| | 頭 | 体 | 結果 |
|---|---|---|---|
| 旧パイプライン | 生成（写真由来） | **生成** | 顔 0.78 だが**指が死に肩が破断**（§37, §38） |

### 常駐なしで TRELLIS を回せた

`adapters/trellis/oneshot.py`（新規）。`trellis_runner.py` はライブラリなので、
`trellis2` env でサブプロセスとして起こし、1枚生成して終了させる。
**プロセス終了で VRAM が完全解放される**ので常駐が要らない
（リポジトリの「各モデルは独立サブプロセス」の約束どおり）。

実測: **読み込み 95.6s + 生成 176.2s = 271.9s**、GPU1、出力 33.9MB / **706,749頂点**。
終了後 GPU1 は 24,027 MiB に復帰（残留なし）。
Rocketbox の頭（1,921頂点）の **368倍の密度**で、これが同一性が生き残る理由。

### 二つの間違いを訂正した

**(1) 投影は要る。** TRELLIS.2 は写真から PBR テクスチャを生成するので投影が
不要かと思い（見た目は投影前のほうが鮮やかだった）測ったところ、

**(2) 生成復元した写真を同一性の源に使ってはいけない。**

素の `subject-a_head_1024.png`（280px）が 0.7732。§40 が「復元は顔を変えうる」と
警告していたとおり。**解像度で選ばず、加工の無い写真を選ぶこと。**

生成頭はバスト形状で顔が枠を占めるため、`--frame head`（余白1.25）では
**SCRFD が顔を検出できない**。`--frame-margin 1.6` で顔 342px、検出可。
`--frame full` でも通るが 241px で密度が落ちる。

## 11. リスクと未解決点

- **モーフ差分をどう扱うか（最大の未確定点）**。基準形状を f(x) で動かしたとき、
  57個のモーフ差分も局所ヤコビアンで変換すべきか、生のまま置くか。
  既定は**生のまま置く** — `transfer_expr.py` が「幾何を変えずに差分だけ移す」で
  実測無損失（ArcFace 0.6617 → 0.6617）だった前例に倣う。M1 で目視確認する
- **68点ランドマーク対応の手作業**。素体2体分を手で張る必要があり、品質がここで決まる。
  ICT 側は `vertex_indices.json` の `idx_to_landmark_verts`（68点）が既にあるので、
  作業はテンプレート側の68頂点を拾うことだけ
- **RBF の外挿**。顔だけ動かして首から下を固定すると継ぎ目が出る。フォールオフが要る
  （`transfer_expr.py` の near 0.012 / far 0.030 と同じ考え方）
- **髪がついてこない**。頭の形を変えると `Hair`（12,868v）が浮くか埋まる。
  spring bone の初期姿勢との整合も要確認
- **MICA は動かない**。`vendor/MICA` にチェックポイント479MBはあるが FLAME2020 の
  `generic_model.pkl` が無く、`envs/setup_face.sh:118-140` が MPI 登録・ライセンス同意を
  要求して取得を拒否している（§39）。**MICA を前提にしない。**
  識別形状は MIT の ICT-FaceKit で解く
- 男女2体になることで、ランドマーク対応・デフォルメ係数・髪型セットがそれぞれ2組要る。
  **M1 のコストはおよそ倍。** 女性素体で通し切ってから男性素体を同じ手順に流す
- **`Body` のマテリアルは服**（Tops/Bottoms/Shoes）。「本人の服装を反映する」は M1〜M2 の範囲外。
  写真から反映されるのは顔と体型だけ
