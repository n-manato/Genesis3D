# 05 — 実測メモ（2026-08-20）

Phase 2〜3 の構築中に実機で測った結果。設計時の想定と食い違った点を中心に記録する。
数値はすべてこの1台（RTX 3090 ×2 / i9-10900X 20T / Ubuntu 20.04）での実測。

## 1. TRELLIS.2 の既定値がパイプラインを実用外にしていた

`trellis_runner.py` の既定は `decimation_target=1,000,000` / `texture_size=2048` /
`remesh=True`。さらに `_SIMPLIFY_LIMIT = 16,777,216` のため事前の `mesh.simplify()`
が実質無効で、数百万面のメッシュがそのまま `o_voxel.postprocess.to_glb` に渡る。

| 設定 | 所要 | 結果 |
|---|---|---|
| 既定（decimation 1,000,000 / tex 2048） | **>22分**（900秒でHTTPタイムアウト、その後も継続） | 失敗 |
| 修正後（decimation 120,000 / tex 1024） | **25〜30秒** | 成功 |

**50倍以上の差**。GPU利用率は0%で、7スレッドが100% CPU に張り付く純粋なCPU処理だった。

VRM アバターの実用ポリゴン数は3万〜15万。参考に実在アバター
`KEHAI/Live2D Characters/vrm/subject_a.glb` は **94,875三角形**。100万は約10倍過剰。

→ `configs/models.yaml` の `mesh_settings` で候補生成 120,000 / 仕上げ 200,000 に設定。
アダプタは必ず明示的に渡す（既定に落とさない）。

## 2. 解像度1024は24GBカードで動く。かつ全身像には必須

`trellis-service/README.md` は「24GBカードでは 512 に留めること。GLB抽出時のピークVRAMは
24〜30GB」と警告している。しかし TRELLIS.2 が17GB常駐した状態で **1024 は OOM せず29秒で完走**した。

同一入力・同一ジョブでの比較（全身キャラクター）:

| 解像度 | 所要 | 三角形 | 連結成分 | 幾何の質 |
|---|---|---|---|---|
| 1024 | 29.3秒 | 113,490 | 6,044 | **胴体・腕・脚がすべて連結。目鼻口が形成される** |
| 512 | 14.4秒 | 117,238 | 3,754 | 肩と袖が分離。**顔がのっぺらぼう** |

連結成分の数は 1024 の方が多いが、これは髪の房などの細部が分離しているためで、
**本体の連結性は 1024 の方が明確に良い**。連結成分数を単純に減点指標にしてはいけない。

→ `configs/styles.yaml` の quality preset に `resolutions` を追加。
`high` は [1024, 512]、`maximum` は [1024, 1024, 512, 512]。高解像度が OOM しても
低解像度の候補が残る（要件§30）。

## 3. 背景除去は RMBG-2.0 を使う。rembg では装飾が消える

既存 Nexus サイドカー `:8000/remove-bg`（rembg / u2net）と RMBG-2.0 を同一画像で比較。

| 手法 | 結果 |
|---|---|
| rembg (u2net) | 背景とエフェクトは除去。しかし**魔女帽子をキャラクターごと削除** |
| RMBG-2.0 (BiRefNet 220M) | **帽子・うさぎの飾りを保持**し、背景とキラキラのみ除去 |

帽子・武器・獣耳のような大きな装飾はキャラクターの同一性そのものなので、
精度を優先して RMBG-2.0 を採用。重みは既に HF キャッシュにある（4.7GB）。
`transformers` の remote code が `kornia` を要求する点に注意。

## 4. 前処理では入力の構図の悪さは救えない

バストアップ肖像（暗背景＋キラキラ）で試したところ、RMBG-2.0 で背景を完全に
除去しても3D側のアーティファクトはほぼ変わらなかった。原因は背景ではなく
**入力が全身像でないこと**と**つばの広い帽子**。

→ 前処理に「見切れ検出」を実装した。当初は被写体の高さ比 >0.95 で判定していたが、
バストアップ像は 0.92 程度にしかならず検出できなかった。**画像の端に接しているか**で
判定するよう変更し、正しく検出できるようになった。

```
バストアップ  → "被写体が画像下端で見切れている。全身像ではないため VRM 用の
                 脚部・足元が推定されず、リギングが破綻する可能性が高い"
全身像        → 警告なし
```

## 5. 実用アバターは watertight ではない — 評価で減点してはいけない

実在の製品品質アバター `subject_a.glb` の静的解析:

```
三角形 94,875 / 頂点 81,750 / オブジェクト 10
boundary edges 63,681 / 連結成分 2,490 / 重複頂点候補 4,846 / watertight: false
```

衣装・髪・目が別オブジェクトで、UVシームで頂点が分割されているため当然こうなる。
`watertight == false` や「連結成分が多い」を単純に減点にすると、**正しく作られた
アバターほど低スコアになる**。Geometry / Topology スコアはこの実測値を基準に較正する。

## 6. VRM Add-on の API で踏んだ点

- humanoid のプロパティは **snake_case**（`left_upper_arm`）。VRM仕様の camelCase
  （`leftUpperArm`）で `getattr` すると単語1つのボーン（hips/spine/chest/neck/head）
  しか割り当たらず、**見た目は成功して中身が壊れた VRM** ができる。実際 24本中5本しか
  割り当たっていなかった。必須ボーンの割当漏れは書き出し前に停止するようにした。
- `--factory-startup` ではアドオンが読まれないので、`.vrm` を扱うスクリプトは
  明示的に `addon_utils.enable()` する必要がある。
- ボーン名の照合は文字列の末尾から `l`/`r` を削るような処理をしてはいけない
  （`shoulder` → `rightshoulde` になる）。接頭辞から左右を構造的に取り出す。
  VRoid は `J_Bip_C_Hips` / `J_Bip_L_UpperArm`、補助骨は `J_Sec_` / `J_Aim_` /
  `J_Roll_` / `J_Adj_`。優先度を付けて `J_Bip_` を優先し、目だけは `J_Adj_L_FaceEye`
  を採る。これで実物VRMから必須17本＋任意7本の計24本を正しく取得できた。

## 7. ジョブが永久に running のままになるバグ

`finish_job()` が `progress=None` を渡し、`progress INTEGER NOT NULL` に対して
`UPDATE ... SET progress=NULL` を実行して IntegrityError。**UPDATE 全体がロールバック
されるため、失敗したジョブが running のまま残り、エラー内容も失われていた**。

→ `update_job()` は値が `None` のフィールドを「変更しない」意味として除外するようにした。

## 8. TRELLIS.2 はネイティブ拡張内で SIGTERM に応答しない

放棄されたリクエストを止めようと SIGTERM を送ったが、`o_voxel` の C 拡張内に
入っていたため Python がシグナルハンドラを実行できず、40秒待っても終了しなかった。
SIGKILL で即座に終了し、GPU1 の17GBが解放された。

Gateway 側は `TRELLIS_PIN_VRAM=1`（Always Running）で管理しており、**kill後5秒で
worker が自動再起動、85秒で重みロード完了**して元の状態に復帰した。Gateway の
自己修復は設計通り機能する。

## 9. メッシュ修復は「やりすぎ」が最大のリスク

初版の実装（`remove_doubles` あり / `speck_ratio=0.005` / 法線再計算あり）で
面の18.8%が消え、**Tシャツ全面に穴と黒斑**が出た。原因は2つ:

- `remove_doubles` は UV シームのために意図的に分割された頂点を座標だけ見て
  マージするため、テクスチャ付きメッシュでは UV が壊れる
- `speck_ratio` が広すぎ、表面の一部である小さな連結成分まで除去した

→ 頂点マージと法線再計算を既定で無効化し、`speck_ratio` を 0.0002 に下げた。
結果、面損失 5.6% で目視の劣化なし。閾値10%を超えたら「修復した」と主張せず
修復前のメッシュを使うようにした（穴を作るより無修復の方が良い）。

| 設定 | 面損失 | 見た目 |
|---|---|---|
| 初版 (merge有 / 0.005) | 18.8% | Tシャツに穴・黒斑 |
| 現行 (merge無 / 0.0002) | 5.6% | 劣化なし |

## 10. 評価器は目視判断と一致した

DINOv3 (facebook/dinov3-vitl16-pretrain-lvd1689m) でレンダと参照画像の
cos類似度を取り、幾何解析と合わせて重み付けした結果:

| 候補 | overall | identity | back | 目視 |
|---|---|---|---|---|
| res1024 | **7.698** | 8.8 | 7.6 | 全身連結・顔が形成される |
| res512 | 7.021 | 7.0 | 8.1 | 肩が分離・顔がのっぺら |

正面類似度が 0.829 vs 0.723 と明確に差がつき、**自動評価が目視判断と同じ候補を選んだ**。

較正メモ: DINOv3 の cos 類似度は 0.3〜0.9 に収まったので、0.3→0点 / 0.9→10点に
線形写像している。CLIP は重みが未取得（キャッシュに12KBのメタデータのみ）、
ArcFace は未導入のため、`not_measured` に明示して黙って0点にはしない。

## 11. リギングの正規化を親エンプティ経由で行ってはいけない

親エンプティに scale/location を掛けて子メッシュに `transform_apply` しても、
**親の変換は焼き付かない**（子自身の matrix_basis しか適用されない）。
親を削除した時点でスケールが失われ、身長1.6m指定に対し1.0mのまま進んでいた。

TRELLIS.2 は単位AABB（高さ1.0・原点が中心）で返すため、正規化は必須。
各メッシュの `matrix_world` を直接操作して適用するよう修正し、
正規化が効いていなければその場で停止するチェックを入れた。

## 12. バスト構図は res1024 で OOM する。原因は構図ではなく GPU1 の空き

Subject A（実写・バストアップ）で顔トラックを作ろうとして踏んだ。
§2 で「1024は24GBカードで動く」と記録したが、**それは全身像に限った話**だった。

同一サービス・クリーンな状態での比較:

| 入力 | 解像度 | 結果 |
|---|---|---|
| `02_fullbody.png`（全身・アニメ調） | 1024 | **成功 30.9秒**（§2 の29.3秒を再現） |
| 実写バストアップ | 512 | 成功 20.6秒 / 116,246三角形 |
| 実写バストアップ | 1024 | **CuMesh OOM**（`utils.h:43` / `connectivity.cu:772`） |

原因の切り分けに2つの仮説を潰した。**どちらも外れ**:

- **構図（前景占有率）ではない** — `square_pad` の余白を広げ、成功例と同じ
  占有率 0.138（全身像は 0.122）まで被写体を縮めても OOM した。
- **表面の高周波ディテールでもない** — 512へ縮小して1024へ戻し、さらに
  GaussianBlur(0.8) をかけて髪の毛束・ツイードの織り・パールの粒を潰しても OOM した。

真因は **GPU1 の空き容量**。`startupPolicy: "Always Running"` では TRELLIS.2 が
16.8GB を常駐させ、残り 7.3GB で CuMesh を回している。全身像の疎な voxel 体積なら
足りるが、バストの密な体積では足りない。

### 対処: startupPolicy を On Demand にする

`ModelRuntimeConfig.startupPolicy` を `On Demand` にすると `trellis_runner.py:105`
の分岐で `low_vram=True` のままになり、重みは CPU RAM に置かれてステージ実行時だけ
GPU に載る。**アイドル時の GPU1 は 24GB 全空き**になり、CuMesh に十分な容量が渡る。

| policy | 常駐VRAM | 実写バスト res1024 | 所要 |
|---|---|---|---|
| Always Running | 16.8GB | **OOM** | — |
| On Demand | 0GB（CPU RAM） | **成功 4.25MB / 114,397三角形** | 90.1秒 |

実行中の GPU1 ピークは 7.5GB だった。代償はリクエストごとの CPU↔GPU コピーで
90.1秒 対 20.6秒（res512・pinned）。`styles.yaml` の `time_penalty.weight: 0.02` が
示す通りこの計画では時間はほぼ無料なので、**顔トラックは On Demand + res1024 を採る**。

res1024 の目視差は大きい: 目が瞼のある形状として成立し、鼻梁が出て、
パールが1粒ずつ分離し、襟章が独立した形になる。

### 付随して分かったこと

- **OOM は毎回プロセスを汚染する。** §8 の SIGTERM 不応答とは別問題で、
  失敗後の次のリクエストは 0.3秒で即 `CUDA error: out of memory` を返す。
  検証のたびに再起動が要る（`pkill -9 -f "python.*trellis_service.py"` → 約90〜110秒で復帰）。
  **OOM した直後の測定結果は無効**なので、必ず再起動してから測り直すこと。
- **`Always Running` では worker が自動再起動するが、`On Demand` では遅延起動**になる。
  後者では手動で `TRELLIS_PIN_VRAM=0 bash run.sh` を起動するか、Gateway 経由で
  リクエストを投げて起こす必要がある。

## 13. 解像度が本人性を決める。ステップ数はほとんど効かない

§12 で res1024 が通るようになったので、`pipeline.json` が 12 に固定している
sampler steps を `/generate` の Form パラメータとして開けた（0=既定のまま、
つまり未指定なら従来と完全に同一の挙動）。

あわせて **ArcFace を導入した**（`insightface` + `antelopev2`、CPU 実行、408MB）。
`realistic_jrpg` の最大重み identity(0.25) が本来見るべき指標がこれまで無かった。

同一入力・同一シードでの実測:

| 候補 | DINOv3 全体 | DINOv3 顔クロップ | **ArcFace** | 所要 |
|---|---|---|---|---|
| res512 / steps=12 | 0.7440 | 0.5025 | 0.2449 | 20.6秒 |
| res1024 / steps=12 | 0.7874 | **0.6529** | 0.3269 | 90.1秒 |
| res1024 / steps=30 | **0.8243** | 0.5992 | **0.3383** | 179.7秒 |

**解像度が支配的なレバー**。512→1024 で ArcFace +0.082（+33%）。目視でも、
目が瞼のある形状として成立し、鼻梁が出て、パールが1粒ずつ分離する。

**ステップ数はほとんど効かない**。12→30 で ArcFace +0.011（+3%）に対し所要は2倍。
しかも額と生え際に黒い浮遊片が増える。DINOv3 の顔クロップはむしろ悪化と判定する
（0.6529→0.5992）。**指標間で結論が割れるほど差が小さい** ということなので、
顔トラックの既定は **res1024 / steps=12**。steps を上げるのは衣装・装飾を
作り込むときだけにする。

### 3つの指標は別のものを測っている — 取り違えると候補選択を誤る

- **DINOv3 全体** は服の解像感に強く引きずられる。steps=30 を勝ちと判定する（0.8243）。
- **DINOv3 顔クロップ** は顔の造形を見るが、本人かどうかは見ていない。
- **ArcFace** だけが本人性を測る。

`evaluation/score.py:170` は `"face": to10(front)` — 顔スコアに**正面ビュー全体の
DINOv3 類似度をそのまま流用**している。つまり `realistic_jrpg` が顔に割いている
identity 0.25 + face 0.20 = **0.45 が、実際には服の解像感で決まっている**。

## 14. 現状でも既存 Avaturn アバターを上回る。ただし ArcFace 0.33 は低い

作り直す価値があるかを測った。顔検出サイズを揃えた公平比較（検出顔の幅が
同程度になるよう画像全体を拡大してから再検出）:

| モデル | 顔幅 | ArcFace |
|---|---|---|
| 対照: 元写真の別クロップ同士 | 199px | **0.9899**（上限の目安） |
| 既存 Avaturn アバター（`KEHAI/subject_a glb`） | 153px | 0.2477 |
| Genesis3D res512 | 199px | 0.2449 |
| Genesis3D res1024 / steps=12 | 199px | **0.3269** |
| Genesis3D res1024 / steps=30 | 199px | **0.3383** |

- **res512 は既存アバターと同等**（0.2449 対 0.2477）。作り直す意味がない。
- **res1024 は既存アバターを 32〜37% 上回る**。ここではじめて置き換える価値が出る。

ただし絶対値として **ArcFace 0.33 は低い**。一般に同一人物の判定閾値は 0.28〜0.36 で、
0.33 は「同一人物と言えなくもない」境界にすぎない。対照の 0.9899 との差が
そのまま伸びしろで、律速は **元画像が 300×450（顔領域 約130px）しかないこと**。

→ 高解像度の元写真で検証した結果は §15。**予想は外れた。**

## 15. 元画像を2.5倍にしても ArcFace はほぼ動かない。天井は入力ではなくモデル側

§14 で「高解像度の元写真を入手することが他のどのチューニングよりも効果が大きい」と
書いた。所属機関の公式サイトから顔幅 205px の写真を取得して検証したところ、**外れた**。

公式サイトが公開している最大解像度は 1200x800（`_shared/images/` に 1600/1920/2400 は
存在せず 404）。現行の `subject-a.jpeg` は 300x450・顔幅 81px、新規に取得した
`subject_face_downtown_1200.jpg` は 1200x800・顔幅 **205px**（2.5倍）。

同一パイプライン（res1024 / steps=12 / On Demand）で生成し、**共通の参照**に対して
測った。ジョブごとの `scores.json` は各自の `references/rgba.png` と比較するため、
そのままでは異なるジョブ間で比較できない点に注意。

| 生成の元画像 | vs 旧写真 | vs 新写真 | 顔クロップ DINOv3 |
|---|---|---|---|
| 旧 300x450（顔81px） | 0.3598 | 0.3323 | 0.6977 |
| 新 1200x800（顔205px） | 0.3627 | **0.3817** | **0.8178** |
| 対照: 写真同士（旧 vs 新） | — | **0.7907** | — |

- **顔の造形の忠実度は大きく上がった**（顔クロップ DINOv3 0.6977 → 0.8178）。
  目視でも、目の形が整い、肌が滑らかになり、浮遊片がほぼ消える。
- **ArcFace はほとんど動かない**（共通参照で 0.3598 → 0.3627、+0.003）。
  自分自身の参照に対してすら 0.3788 → 0.3823。

決定的なのは対照値。**同一人物の実写どうしは 0.7907** に達するのに、
生成物は元画像を2.5倍にしても 0.38 で頭打ちになる。
つまり **律速は入力画像ではなく TRELLIS.2 の顔ジオメトリそのもの**。

### 帰結: ジオメトリで本人性を稼ぐのは諦め、テクスチャで担保する

顔の形を作り込んでも ArcFace 0.38 前後から動かない以上、本人性は
**実写を UV 投影して顔テクスチャに焼く**（計画の Phase 4-1）で担保するしかない。
高解像度の元画像は、そのテクスチャ源として依然として重要——
`subject_face_downtown_1200.jpg` は顔幅 205px あり、投影素材として 81px 版より遥かに良い。

高解像度化の投資対効果を正しく言い直すと:

- ジオメトリ経由の本人性: **ほぼ効かない**（+0.003）
- 顔の造形の質・アーティファクトの少なさ: **大きく効く**（+0.12）
- テクスチャ投影の素材として: **決定的**（顔の画素数が2.5倍）

## 16. 実写の顔テクスチャ投影で ArcFace が 0.38 → 0.67。本人性はここで稼ぐ

§15 で「本人性はジオメトリでは稼げない。実写を UV 投影して顔テクスチャに焼く
しかない」と結論した。実装して検証したところ、**そのとおりだった**。

実装は2段:

1. `preprocessing/face_projection.py` — 写真を生成メッシュの正面レンダの画角へ整列。
   ArcFace の5点ランドマーク（両目・鼻・口角）から **相似変換**（回転・等方スケール・
   平行移動）を解く。アフィン全体にしないのは、せん断が入ると顔の比率が崩れて
   本人性がむしろ落ちるため。顔領域の楕円マスクをアルファに入れ、レンダのアルファ
   （シルエット）を掛けてメッシュ外へはみ出さないようにする。
2. `blender/project_face.py` — 整列済み画像を正面カメラから UV 投影し、
   既存ベースカラーとマスク合成して焼き直す。

正面〜3/4 が主用途（会話アバター）なら現状で足りる。

### 実装上の落とし穴

`bpy_extras.object_utils.world_to_camera_view` は **`scene.render.resolution_x/y`
のアスペクト比**を使う。`render_views.py` は必ず正方形(res×res)で撮るのに、

二重像になる**。整列に使ったレンダと同じ解像度を必ず設定すること。

## 17. 全身Tポーズを生成して3D化できるようになった。顔と体は別に作る

  配色は OpenPose の規約どおり（ControlNet はこの色で学習されている）。
  比率は 7.5 頭身 canon。**指極 ≒ 身長 なのでキャンバスは正方形**にする —
  縦長にすると手首が画面外に出る。

- `multiview/select_view.py` — 足の見切れをゲートにし、外接矩形の縦横比で

- `envs/setup_imagegen.sh` — conda env `genesis-imagegen`（約15GB）。

| | 値 |
|---|---|
| 生成 6枚（1024²、30ステップ） | 全て正しいTポーズ・全身・足まで写る |
| 外接矩形の縦横比 | 1.026〜1.062（1.0 が理想） |

### 生成画像の顔は本人ではない — 計画の想定どおり

生成した全身Tポーズ画像の顔は ArcFace **0.1986**（実写との比較）。
全身では顔が画面の 5% ほどしか占めないので、当然そうなる。
そのまま3D化した VRM は 0.0637。

| 3D化した VRM（顔投影なし） | 0.0637 |

### 工程6は工程7の後に走らせる。画角は head → full のフォールバック

実装中に3つ踏んだ。すべて「メッシュの顔が平坦だと顔検出が落ちる」に帰着する。

1. **生成した全身画像の顔は 83px しかない。** TRELLIS.2 はそこから顔の造形を
   作れず、のっぺりした顔のメッシュになる（§2 の「res512 で顔がのっぺらぼう」と
   同じ現象が、解像度ではなく**入力の顔の画素数**で起きる）。
2. **平坦な顔は頭部に寄せると逆に検出できなくなる。** 全身の画角で 61px なら
   検出できるのに、頭部に寄せて 311px にすると顔と認識されない。細部が無い顔は
   拡大するほど「顔らしさ」を失う。縮小して再検出する経路も入れたが、
   このケースは救えなかった。
   → `_retexture` は画角 `head`（テクセル密度が高い）を先に試し、落ちたら
   `full` に落ちる。バストアップ入力なら head が通り、生成全身なら full になる。
3. **工程6を工程7より先に走らせていた。** 順序を入れ替えた。
   `STAGES` の順も実行順に合わせてある。

なお **`--frame head` が通る場合は 0.6391** まで出る（バスト入力・手動実測）。
full にフォールバックすると 0.5819。**顔と体を別メッシュで作って接合すれば
head が使えるはず**で、それが本来の姿（計画の `blender/merge_head.py`）。
現状は「体のメッシュに実写を投影する」近道を取っているぶん、この差が残る。

## 18. 顔と体を別メッシュで作って接合する（merge_head）

§17 の「体のメッシュに実写を投影する」近道は、体メッシュの顔が平坦すぎて
画角 `head` が使えず `full` に落ちる。本来の姿である接合を実装した。

`blender/merge_head.py` — 顔メッシュ（実写ポートレート由来）と体メッシュ
（生成Tポーズ由来）を繋ぐ。肩の検出は `blender/mesh_landmarks.py` に切り出して
`project_face.py` と共用する。

接合の考え方:

- **スケールは「頭頂〜肩」の高さを揃える。** 頭部の横幅ではなくこの区間を使うのは、
  体側の頭は作り直す対象で形が当てにならないのに対し、肩の位置は胴の形状から
  決まるので安定しているため。実測では幅基準だと 0.417、高さ基準だと 0.278 と
  大きく食い違い、高さ基準が正しかった。
- **水平位置は頭部帯の中心で合わせる。** 全体の重心だとTポーズの腕に引っ張られる。
- **首の途中で切って少し重ねる。頂点はマージしない。** UV シームのために分割された
  頂点を座標だけで繋ぐとテクスチャが壊れる（§9）。実用アバターは watertight で
  なくてよい（§5）。

### 結果

| | ArcFace 正面（2048レンダ・顔135px） |
|---|---|
| 投影ルート（体に直接投影） | 0.5810 |
| **接合ルート（merge_head）** | **0.5946** |

接合の実測値: 体は 高さ1.0 / 肩 z=0.344 / 頭部帯 0.156、顔メッシュは頭部帯 0.563 →
スケール 0.278。結合後 120,059頂点・168,483ポリゴン・マテリアル2。

リギングまで通り、**VRM の検証は必須17本の欠落なし・任意7本すべて present**
（upperChest / 左右shoulder / 左右toes / 左右eye）・身長1.6m・原点足元。
成果物は `subject_a/subject_a_fullbody.vrm`（10.8MB）。

### 差が小さい理由 — 律速は「見る大きさ」に移った

接合ルートの顔メッシュ単体は ArcFace 0.6836 出ていた（バスト画角）。それを
全身に載せて 2048 でレンダすると顔は135pxで 0.5946 になる。**メッシュの質ではなく
レンダ時の顔の画素数が効いている。** 全身を1枚に収める限りこの制約は外れない。

会話アバターのように上半身で映す用途なら差は開くはずで、そこが接合ルートの
利点になる。全身俯瞰が主用途なら投影ルートで十分。

## 19. 二トラック構成をパイプラインに組み込んだ。投影は接合の「前」

§18 の接合を工程として入れた。`face_image` が指定されたときだけ走る
（指定が無ければ従来どおり単一メッシュ）。

```
mesh_repair → head_merge → retexture → rigging
```

`head_merge` の中身:

1. 実写から頭部＋肩を切り出す（`preprocessing/head_crop.py`、顔検出基準）
2. RMBG-2.0 で背景除去
3. TRELLIS.2 res1024 で顔メッシュ（顔だけなので密度が低く 1024 が通る）
4. `repair_mesh.py`
5. **実写を顔メッシュへ投影**（`project_face.py`）
6. `merge_head.py` で体に接合

工程6の投影ロジックは `_project_face` ヘルパーに切り出し、`head_merge` と
`retexture` で共用する。`head_merge` が成功したら `retexture` は**何もしない**
（二度貼ると質が落ちる）。

### 5 と 6 の順序が決定的だった

最初は「接合してから投影」で組んだ。結果は **ArcFace 0.3445** で、
単一メッシュへの投影（0.5810）より悪かった。原因は画角:

| 投影の対象 | 整列レンダの顔幅 | ArcFace 正面 |
|---|---|---|
| 接合後の全身に投影 | 65.5px | 0.3445 |
| **接合前の顔メッシュに投影** | **248.8px** | **0.6634** |

顔メッシュはバスト形状なので、全身に載せる前なら顔が画面の大半を占める。
載せてからでは全身の一部でしかない。**投影は必ず接合の前に行う。**

### 到達点

| 構成 | ArcFace 正面 | 3/4 |
|---|---|---|
| 投影のみ（単一メッシュ） | 0.5810 | — |
| 手動接合（投影済み顔メッシュを流用） | 0.5946 | 0.4764 |
| **パイプライン二トラック** | **0.6634** | **0.5839** |
| 対照: 実写どうし | 0.7907 | — |

実写どうしの上限に対して **84%**。所要 220秒、VRM 13MB、
必須17本＋任意7本すべて割当・身長1.6m・原点足元。

### 残る見た目の問題

顎と頭頂に明るい帯が出る。マスクの縁だと考えて首まで伸ばしてみたが、帯は
消えず ArcFace は 0.6634 → 0.6455 に下がった。**原因は頭部メッシュ自身の
テクスチャが淡いこと**で、マスクの位置では解決しない。

低周波の色をメッシュ側へ寄せる `--color-match` も実装したが、寄せる先の顔が
本人ではないので本人性を削る（0.5824 → 0.5520）。**既定は無効**にしてある。
マスク端のぼかし幅を 0.35 → 0.55 に広げる方は本人性を下げないので既定にした。

## 20. ポートレート1枚から全身リグ付き VRM まで通った

工程2をパイプラインに組み込み、二トラック構成と繋げた。**画像1枚を投げるだけ**で
脚と足のある実写似のアバターが出るところまで到達した。

```
preprocess → multiview → geometry → render → evaluate
           → mesh_repair → head_merge → retexture → rigging → vrm_export → validate
```

`_multiview` は **工程1の見切れ警告があるときだけ**走る。高さ比ではなく端への
接触で判定するので（§4）、バストアップ入力を確実に拾い、全身入力では何もしない。
走ったときは元の実写を `params.face_image` に立てて、顔は `head_merge` が実写から作る。

### 実測（`subject_face_downtown_1200.jpg` 1枚だけを入力）

| | 値 |
|---|---|
| 総所要 | 322.6秒 |
| 参照ビュー | 4シード生成・不採用0・縦横比 1.03〜1.06 |
| 接合スケール | 0.2778（頭部帯 0.156 / 0.563） |
| **ArcFace 正面** | **0.7056** |
| VRM | 13MB / 必須17本＋任意7本すべて割当 / 1.6m / 原点足元 |

対照の 0.7907（実写どうし）に対して **89%**。入力の与え方別に並べると:

| 入力の与え方 | ArcFace 正面 |
|---|---|
| バストを直接3D化（顔投影なし） | 0.3627 |
| 生成Tポーズを3D化（顔投影なし） | 0.0637 |
| 生成Tポーズ＋実写を体に投影 | 0.5810 |
| 全身画像＋実写を明示指定（二トラック） | 0.6634 |
| **ポートレート1枚（全自動）** | **0.7056** |

全自動が最も良いのは、`head_crop` に**前処理済み rgba ではなく元ファイル**を
渡しているため。顔の画素数が最大のまま顔メッシュに入る。

### 踏んだバグ: 顔用の実写に rgba を渡すと接合が壊れる

最初の実装では `params.face_image` に `references/rgba.png` を立てていた。
rgba は被写体を正方形に詰め直してあるので、そこから頭部を切ると
**画像のほぼ全体**が取れる（実測 754px 中 `crop_box [4,0,684,711]`）。
結果、顔メッシュに胴が入りすぎて肩の検出位置がずれ、頭部帯が
0.563 → 0.344 に縮み、接合スケールが 1.64 倍ずれて**顎が切り落とされた頭**になった
（ArcFace 0.4430）。元ファイルを渡すよう直して 0.7056。

`merge_head.py` に、頭部帯基準と頭幅基準のスケール推定が 50% 以上食い違ったら
警告を出すチェックを入れた。**値の上書きはしない** — どちらが正しいかは入力次第で、
黙って別の値に差し替える方が危ない。

### 残っている見た目の問題

顎に投影マスクの端が帯として見える。§19 の通りマスクを伸ばしても消えず
（原因は頭部メッシュのテクスチャが淡いこと）、色合わせは本人性を削る。未解決。

## 21. 顎の「帯」の正体は接合の切断位置だった

§16 以降ずっと「顎に明るい帯が出る」と記録し、投影マスクの縁だと考えて
マスクを伸ばしたり色を合わせたりしたが、どれも効かなかった。切り分けをやり直した。

顔メッシュを**投影の前後**で同条件レンダして比べたところ、**どちらにも帯は無い**。
つまり投影の問題ではなく、**接合で発生している**。

さらに体メッシュ単体をレンダすると、生成Tポーズ由来の体は**もともと首が長い**。
`merge_head.py` の切断位置は既定 `--neck-offset 0.030`（肩から全高の3%上）で、
体の頭部帯が 0.156 しかないため、この位置は**ちょうど顎の線**に来ていた。
そこで頭側メッシュの顎と体側の長い首が突き合わさり、色と形の段差が帯に見えていた。

切断位置を振って実測:

| `--neck-offset` | 見た目 |
|---|---|
| 0.030（旧既定） | 顎の線で切れて帯が出る |
| **0.012** | **帯が消える。首も自然** |
| 0.065 | 口のあたりを切ってしまう |
| 0.100 | 目のあたりを切ってしまう |

→ 既定を **0.012**（首の中ほど）にした。ArcFace は 0.7056 → 0.7015 でほぼ不変、
見た目だけが直る。

### スケールの基準も変えた

「頭頂〜肩」の高さで合わせていたが、この区間は**頭＋首の合計**なので、
首の長さが違うメッシュ同士では頭の大きさが揃わない。頭部帯の中の
**最大横幅**（同じ人物なら一致するはずの量）を基準に変更した。
今回の入力では両基準が 0.2719 対 0.2776 とほぼ一致し、
食い違ったら警告を出すチェックも残してある。

### 経緯の反省

「投影マスクの縁」という最初の見立てのまま §16・§19 で2回対処を試み、
どちらも外している。**投影の前後で切り分ける**という一手を早くやっていれば
すぐ分かった。症状の出る工程を先に特定すること。

## 22. 二トラック構成では評価の基準を「ジオメトリの実際の入力」にする

工程2が参照ビューを生成する構成にしたあと、評価器が壊れていた。候補は
**生成したTポーズ画像**から起こしたのに、比較の基準が元の実写のままだったため。

同一ジョブ（`056e48908c92`）で基準を変えて測り直した:

| 基準 / 重み | identity | face | body | overall |
|---|---|---|---|---|
| 元の実写・全指標（旧） | 0.00 | 2.89 | **1.09** | **1.875** |
| 生成ビュー・identity/face 除外（新） | — | — | **7.47** | **8.159** |

body が 1.09 というのは「Tポーズの全身レンダとバストアップ写真を比べた値」で、
測っているのは姿勢と構図の差でしかない。基準を揃えると 7.47 になり、
**候補間の差が意味を持つようになる**。

### identity と face は重みから外す

後段で顔を差し替える構成では、候補はすべて同じ生成画像由来なので顔で区別が
つかない。実測でも全候補が `identity=0.00` で、選択に一切寄与していなかった。
`--exclude-metrics identity,face` で外し、**外した分は残りへ比例配分**する
（合計を保って 0..10 の尺度を維持）。realistic_jrpg の場合:

```
body 0.20 → 0.338 / hair,clothes,texture 0.10 → 0.169
topology,back,rigging 0.05 → 0.085
```

顔の重み 0.45 が体・髪・衣装・テクスチャへ回る。**この構成で選ぶべきは体の質**
なので、これが本来の配分。

### 実装

- `evaluation/score.py` に `--reference` と `--exclude-metrics` を追加
- `orchestrator/pipeline.py` の `_evaluate` が、ジオメトリに実際に渡した画像を
  `--reference` に渡す。`params.face_image` があれば identity/face を外す
- `output/job.json` の `evaluate` に `reference` / `excluded_metrics` / `weights`
  を残す。**なぜその候補が選ばれたかを後から追えるようにするため**

### 回帰

全身画像を直接入れる従来の経路では、工程2も head_merge もスキップされ、
基準は元画像・全指標のまま。実測 `7.72 / 7.07` で、§2 の記録値
`7.70 / 7.02` と一致する。

## 26. 多視点投影は実装したが使えない。整列が2Dの相似変換だから

§25 で「素材が無い」と書いたが、探し直したらイベント写真に角度付きがあった。

|---|---|---|---|---|
| marcomm-84 | -39.9° | 57px | 0.576 | 式服・逆光 |
| marcomm-67 | +32.2° | 70px | 0.522 | 式服＋角帽 |
| marcomm-80 | -30.4° | 57px | 0.610 | 着席 |
| **marcomm-82** | **-24.9°** | 64px | **0.677** | グレー上着・照明良好 |
| marcomm-77 | +20.9° | 86px | 0.598 | **マスク着用**（使用不可） |

`blender/project_face.py` を多視点対応にした（`--view AZIM:PATH` を繰り返す。
負の方位角は `--view=-30:...` と `=` で繋ぐ。空白区切りだと argparse が
オプション名と誤認する）。カメラ方位角は **−yaw**（被写体が yaw Y に見えるのは
方位 −Y から撮ったとき）。

### 結果: 数値は改善、見た目は悪化

| | 正面 | 3/4 | 左 | 右 |
|---|---|---|---|---|
| 正面のみ | 0.3821 | 0.2993 | 0.0848 | 0.0777 |
| 3視点 | 0.3861 | 0.2992 | **0.1482** | **0.0408** |

左側面の ArcFace は +75% だが、**目視では頬に暗い染みが乗り、側面に幽霊のような
顔が二重に貼り付いている**。右は数値も見た目も悪化（素材が式服＋角帽のため）。

**原因は整列の方式**。`preprocessing/face_projection.py` は5点ランドマークから
**2Dの相似変換**（回転・等方スケール・平行移動）を解いている。これは面外回転を
表現できない。yaw −25° の写真を方位 25° のメッシュに貼っても、鼻や頬の
奥行き方向のずれが残って二重像になる。

→ **既定は正面のみのまま**（パイプラインは `--photo` を使い続ける）。
多視点を実用にするには、面外回転を扱える整列——メッシュ自身の形状を使った
対応付けか 3DMM フィッティング——が要る。素材の問題ではなく手法の問題だった。

### 指標が誤誘導した例として記録する

ArcFace は左側面で改善を示したのに、実物は明らかに悪い。横顔は正面参照に
対してそもそも照合できない（§25 で未投影の側面が −0.007 だった）ため、
**この領域では ArcFace の差は意味を持たない**。数値だけを見て採用していたら
品質を落としていた。側面の評価には別の指標が要る。

## 28. 【重大】このパイプラインが出した VRM は一度もスキンされていなかった

3Dモデルの品質確認でポーズを付けたところ、**骨を回してもメッシュが1mmも動かなかった**。
調べると `character.vrm` の `skins` が **0**。頂点属性に `JOINTS_0`/`WEIGHTS_0` は
あるのに、それを骨に結ぶ skin 定義が無く `node.skin = null`。読み込むと
頂点グループ0・Armatureモディファイア無しになる。**アニメーションできない VRM**。

**これは私の変更で入ったものではない。** README が成功例として挙げている
旧ジョブ `6231c0823944`（79.9秒でVRM到達）も `skins=0` で、
**このパイプラインが出した VRM はすべて動かない**。

### 原因: heat map が例外を投げずに全ウェイト0で完了する

`blender/autorig.py` の `bind()` は `ARMATURE_AUTO`（heat map）を呼び、
**ARMATURE モディファイアの有無だけ**で成功を判定していた。実測すると:

```
頂点グループ 167個          ✓
Armature モディファイア      ✓
deform 骨 167/167           ✓
ウェイトが入った頂点  0 / 121,228   ← これ
```

Blender の heat map は解が出ないとき**警告のみで例外を投げない**。
glTF エクスポータは「スキンする対象が無い」と判断して skin を書かず、
`skins=0` の VRM ができる。頂点グループも骨の割当も揃っているので、
検証（必須17本＋任意7本＋身長＋原点）は**全部通る**。

image-to-3D の出力は連結成分 2,337・非多様体エッジ 73,049 で、
heat map は原理的に解けない形状だった。

### 対処

| 方式 | ウェイトが入った頂点 |
|---|---|
| `ARMATURE_AUTO`（heat map） | **0 / 121,228** |
| `ARMATURE_NAME` | 0 / 121,228 |
| **`ARMATURE_ENVELOPE`** | **121,699 / 121,699（100%）** |

1. `bind()` は**ウェイトが入った頂点数を必ず数え**、5割未満なら次の方式へ落ちる。
   どれも駄目なら `SystemExit` で止める（動かないVRMを成功として出さない）。
2. エンベロープは距離だけで決まり境界が階段状になるので、
   `vertex_group_smooth`（factor 0.5 / 8回）で後処理する。
3. `blender/export_vrm.py` の検証に**スキン検査を追加**。必須ボーンの欠落と
   同格で `sys.exit(2)`。既存の壊れた VRM で発火することを確認済み。

修正後: `bind_method: ARMATURE_ENVELOPE` / `weighted_ratio: 1.0` /
**VRM `skins: 1`（167ジョイント + inverseBindMatrices）**。
ポーズを付けると外接寸法が 幅 1.577→1.102・高さ 1.600→1.563 と実際に変形する。

### 残る問題: 曲げると衣装が裂ける

動くようにはなったが、変形の質は粗い。ジャケットが裂ける。
原因はウェイトではなく**メッシュが2,337個の連結成分に分かれている**こと —
ジャケットの断片が別々の骨に付いて離れる。ウェイト平滑化の効果は限定的だった。

根本対処は連結成分の統合だが、UVシームの頂点をマージするとテクスチャが壊れる
（§9）。UniRig の導入か、シェル統合を UV を保ったまま行う方法が要る。

### 教訓

**「工程が ok を返した」と「成果物が使える」は別物。** この工程は
`meshes_bound: 1` と報告し続けていた。数えていたのは*モディファイアの有無*で、
*ウェイトの有無*ではなかった。検証は成果物の**用途**（アニメーションできるか）
で書くこと。

## 29. 衣装が裂ける原因は「首の骨の影響範囲」だった

§28 でスキニングを直した結果、動くようにはなったが**曲げるとジャケットが裂けた**。
連結成分が 2,337 に分かれているせいだと考えて2つ手を打ったが、どちらも外した。

1. **ボクセル代理メッシュ経由のウェイト転送** — 繋がった代理（23,410頂点）で
   ウェイトを解いて実メッシュへ空間転送する。UV を壊す操作を代理側だけで
   完結させられるので手法としては正しい（§9 の教訓を守れる）。
   実装して 100% ウェイトが入るようになったが、**裂けは変わらなかった**。
2. **ウェイト平滑化** — 効果は限定的。
3. **正規化の確認** — 書き出し後の VRM は 1頂点4本・合計 1.000 で既に正しく、
   ここは原因ではなかった。

### 骨ごとに動かして切り分けた

| 動かした骨 | 結果 |
|---|---|
| 腕のみ | **無傷** |
| 脚のみ | **無傷** |
| 前腕のみ | **無傷** |
| **首のみ** | **ジャケットの胴が裂ける** |

原因は**首の骨の影響範囲**だった。テンプレート VRM は全ての骨に
`envelope_distance = 0.25` という**固定値**を持つ。首の長さは 0.0737 なので
自分の 3.4倍、1.6m 換算で 25cm の球が影響範囲になり、胸とジャケットを巻き込む。
指先の骨に至っては 26倍。

### 対処: 上限だけを骨の長さに比例させる

```
envelope_distance = min(元の値, 骨の長さ × 1.35)
```

**全部を長さ比例に置き換える案は過補正だった**（腕の影響範囲まで狭まり袖が
細い筋状に伸びた）。係数を振って決めた:

| k | 首 | 腕+脚 |
|---|---|---|
| 元（固定 0.25） | 裂ける | 無傷 |
| **1.35** | 軽微 | **無傷** |
| 0.8 | 軽微 | **袖が裂ける** |
| 0.5 | 軽微 | **袖が裂ける** |

上腕は長さ約 0.25 なので k=1.35 では上限 0.34 > 0.25 で**元の値のまま**、
0.8 以下だと 0.2 に絞られて壊れる。**効いていたものは触らない**のが正解だった。

### 結果と残り

Aポーズ（腕を下げる＋膝を曲げる）は実用的な見た目になった。
首を大きく振ったときのジャケットの乱れは軽減したが**完全には消えていない**。
根本的には、衣装を別メッシュに分けて手でウェイトを塗るか、UniRig のような
学習ベースのリギングが要る。テンプレート転写の限界。

### 教訓

「連結成分が多いから」という**もっともらしい仮説に2手も費やした**。
骨を1本ずつ動かして切り分ければ最初の1手で分かった。
**症状を出す最小の操作を先に特定すること。**

## 30. 「連結成分が2,000個」は UV シームだった。浮遊片除去が表面を削っていた

品質確認でメッシュを数え直したところ、成果物の VRM は連結成分 2,159・
最大でも全体の 3.3% で、「破片の山」に見えた。しかし **距離 1e-5（0.01mm）で
溶接すると 37 成分・最大 90.8%** になる。

| 状態 | 連結成分 | 最大の占有率 |
|---|---|---|
| 書き出しのまま | 2,159 | 0.0327 |
| **1e-5 で溶接** | **37** | **0.9081** |

つまり幾何的には分断されておらず、**2,159 という数字はすべて UV シームによる
頂点分割**だった。§5 が「実用アバターは watertight ではない」と警告していたのは
まさにこれ。§29 で「連結成分が数千に分かれている」と書いたのは**不正確**だった。

### これが浮遊片除去を壊していた

`blender/repair_mesh.py` は辺の共有だけで成分を数え、**本体面積の 0.0002 倍**
未満を浮遊片として削っていた。ところが「本体」が全体の 3% しかないので
閾値が極端に小さくなり、しかも UV 島と本物のゴミが区別できない。

| | 除去した成分 | 面損失 |
|---|---|---|
| 旧（辺の共有で判定） | 5,665 | **8.28%** |
| **新（位置で溶接して判定）** | **24** | **1.07%** |

**正常な表面を 7.2% 削っていた**。目視でも額の黒点（本物の浮遊片）が残る一方で、
表面に穴が開いていた。溶接IDを作って面を繋ぐ方式に変更（メッシュ自体は
一切変更しないので UV は無傷）。

## 31. 髪が透けるのは薄いシェル × 裏面カリング

側面や 3/4 から見ると髪が透ける件。原因は**マテリアルが片面表示**だった。
書き出した glTF の `doubleSided` が未設定で、仕様上の既定は false。
image-to-3D の髪は板状の薄いシェルになるので、内側が見える角度で消える。

Blender 側で `use_backface_culling = False` にしても **VRM アドオンの書き出しは
これを反映しない**（実測: `doubleSided` が出力されなかった）。書き出した GLB の
JSON チャンクを直接書き換える方式にした。

```
GLB = [12Bヘッダ][JSONチャンク][BINチャンク]
JSON を書き換えると長さが変わるので、4バイト境界にスペースで詰め直し、
チャンク長とファイル全長を書き直す。ここを間違えると読めない GLB になる。
```

Blender の EEVEE は既定で両面描画するため**レンダでは差が出にくい**が、
**three.js など glTF を仕様どおり解釈するビューアでは決定的**に効く。
Web ビューアで見る前に必ず入れること。

## 32. Web ビューア（three.js）

マウスでカメラを動かせるビューアを2種類用意した。

| | 面数 | テクスチャ | 置き場 |
|---|---|---|---|
| **ローカル版** `subject_a/viewer/` | 178,716（フル） | 2048 | `../subject_a_fullbody.glb` を読む |
| **Artifact 版** | 80,422（45%に間引き） | 1024 | ページに base64 で同梱 |

### Artifact に同梱する必要があった理由

Artifact の CSP は**外部への fetch を許さない**。`assets` capability もこの環境では
使えないため、モデルはページ本体に埋め込むしかない。base64 は元の 4/3 倍になるので、
16MB の上限に収めるには **5.67MB（→base64 7.56MB）まで落とす**必要があった。
面 45%・テクスチャ 1024 でここに収まる。

### three.js のバージョン選択

`examples/js`（クラシックスクリプト。`THREE.GLTFLoader` / `THREE.OrbitControls` を
名前空間に入れる）は **r147 が最後**で、r152 では 404 になる。ESM + importmap を
避けるなら r147 を使う。r128 でも動くが、両方とも `EXT_texture_webp` に対応している
ことを確認した上で r147 を採った。

### §31 が効いてくる場所

Blender の EEVEE は既定で両面描画するのでレンダでは差が出にくいが、
**three.js は glTF の `doubleSided` を仕様どおり解釈する**。§31 で
`doubleSided: true` を立てていなければ、ビューアで髪が透けて見える。

### ローカル版は `file://` で開けない

`GLTFLoader.load` は fetch を使うので CORS で止まる。
`cd Subject A && python3 -m http.server 8000` → `http://127.0.0.1:8000/viewer/`。
エラーメッセージにこの手順を書いてある。

## 33. 「顔がおかしい」の切り分け — 誤診2回の記録

出力を見た指摘「顔おかしくね?」を追った。**途中2回、原因を誤った。**

### 誤診1: 「顔が横に広く平たい」

頭部の**外接矩形**で測って 高/幅 0.894・奥行/幅 0.734 となり「潰れている」と判断した。
しかし外接矩形は**髪の広がり**を頭蓋の幅として数えてしまう。高さごとの**断面**で
測り直すと 奥行/幅 は 0.966〜0.987 で正常だった。平たいのは胸（0.707）。

### 誤診2: 「接合で壊れている」

接合前と接合後を並べて「接合後が白飛びして髪が薄い」と判断した。しかし
接合前はバスト、接合後は全身をレンダしており、`render_views.py` は
**シーン寸法に応じてライトを配置する**ため露出が変わる。同一画角・同一照明で
撮り直すと接合前後はほぼ同一だった。

**教訓: 比較する2枚は撮影条件を揃えてから見ること。** §29 でも同じ種類の
失敗（もっともらしい仮説に飛びついて2手無駄にした）をしている。

### 測って正常だったもの

| 項目 | 結果 |
|---|---|
| 顔のランドマーク比（目間/目口・口幅/目間・bbox幅高） | 元写真と **1〜2%以内** |
| 頭部断面の 奥行/幅 | 0.966〜0.987 |
| 顔の起伏（額→鼻→顎） | 3.0cm / 頭部高 25.7cm |
| 陰影の光への追従 | 正常（キーライト反転で陰影が動く） |
| 接合による劣化 | なし |

形状・比率・法線はいずれも問題ない。

### 実際に残っている問題

1. **目が細い（しかめ面に見える）** — 素材由来。元写真が笑顔で目が細まっており、
   その状態の眼窩を3D化するとテクスチャと陰影が重なって過剰に暗くなる。
   手元の実写9枚はすべて笑顔・細目なので、どれを選んでも同じ傾向になる。
2. **元写真の照明が焼き付いている** — 対処を試して**失敗**（下記）。
3. **胴体側の浮遊片** — 対処済み（下記）。

### 対処できたもの: 接合後の浮遊片除去

工程7の修復は接合**前**に各メッシュ単体へ掛かるため、自分の本体面積が基準になり
体側の小片が閾値を下回らない。接合後は本体がはっきりするので同じ判定でゴミだけが
浮き上がる。`_head_merge` の最後に `speck_ratio 0.003` で修復を追加した。

閾値 0.0025〜0.006 のどこでも**同じ6〜7片**が消える（その間に隙間があるので
ピアス等の小物は巻き込まない）。実測 面の 2.0%。

### 対処に失敗したもの: de-lighting

写真に焼き付いた照明を「大きくぼかした自身で割る」ことで平坦化する処理を実装し、
強度を振って測った:

| delight | ArcFace | 見た目 |
|---|---|---|
| **0（既定）** | **0.6601** | 自然な肌色 |
| 0.5 | 0.6403 | やや平坦・首に色被り |
| 0.85 | 0.6327 | 白茶けて首に緑の色被り |

**単調に悪化した。** 影部を割ると彩度ノイズが増幅されるためで、低周波の除算という
単純な手法では扱えない。実装は `--delight` として残したが**既定 0（無効）**。
まともに消すには学習ベースの de-lighting が要る。

## 34. 目の開きは素材で変えられるが、肩検出が壊れる

§33 の「目が細い」を素材側から解こうとした。手元の実写11枚について
106点ランドマークから目の開き（瞼の縦横比）を測った:

| ファイル | 顔幅 | 目の開き | 本人度 |
|---|---|---|---|
| subject_face_yaw+32_600.jpg | 70px | 0.399 | 0.522 |
| subject_face_flag_600.jpg | 121px | 0.320 | 0.815 |
| **subject_face_tweed_1200.jpg** | 147px | **0.311** | 0.857 |
| **subject_face_downtown_1200.jpg（現行）** | 205px | **0.241** | 1.000 |

**現行の写真が11枚中もっとも目が細かった。** tweed 版は +29% 開いている。

### 差し替えたら接合が壊れた

tweed 写真で作り直すと **ArcFace 0.696 → 0.532**、頭が小さく胴に沈んだ。

原因は `blender/mesh_landmarks.py` の肩検出。「上から走査して横幅が頭部基準の
1.9倍に跳ねる点」を肩とみなすが、**tweed 写真は髪が広がっており、その膨らみを
肩と誤認**した。頭部帯が 0.563 → **0.218** に縮み、接合スケールが 1.5 倍狂った。

スケールの2系統推定（頭幅基準 0.470 / 頭部帯基準 0.716）は食い違っていたのに、
警告閾値が 0.5 だったため**発火しなかった**（実際の食い違いは 0.34）。
閾値を 0.25 に下げた。

### 併せて踏んだバグ: 工程2のゲートが広すぎた

`rmbg.py` は端に接触するとどの辺でも「見切れの可能性」を出す。工程2のゲートを
`"見切れ" in w` で書いていたため、**Tポーズ全身画像（手が左右端に接する）でも
発火**し、既に全身なのにもう一度全身を生成していた。
脚と足が無いことを示すのは**下端**の接触だけなので `"下端で見切れ"` に限定した。

### 残る課題

目の開きを改善するには肩検出を頑健にする必要がある。髪と肩を区別するには
横幅だけでなく**奥行きの変化**や左右対称性も見る、あるいは顔検出の位置を
基準に頭部範囲を決める方が確実。素材はある（tweed / flag）ので、
検出さえ直れば +29% の改善が取れる。

## 35. 肩検出の作り直し・自動QA・顔テクスチャの解像度

### 肩検出を「首のくびれ起点」に変えた

§34 の通り、素直に「上から走査して横幅が跳ねた点」を肩とすると髪の広がりを
誤認する。上から下へ辿ると幅は **頭頂 → 髪で最大 → 首でくびれ → 肩で急拡大**
と動くので、**先にくびれを見つけ、その下で肩を探す**方式に変えた
（`blender/mesh_landmarks.py`）。髪の膨らみはくびれより上にあるので巻き込まれない。

| 頭部メッシュ | 旧（跳ね上がり） | **新（くびれ起点）** |
|---|---|---|
| downtown 由来 | 0.563 | 0.578 |
| **tweed 由来（髪が広い）** | **0.218** ← 破綻 | **0.547** |

`confidence` を 3 段（くびれ検出 1.0 / 跳ね上がり代用 0.5 / fallback 0.0）にした。

### ただし目の改善は取れなかった

目の開きが +29% の `subject_face_tweed_1200.jpg` で作り直しても ArcFace 0.696 → 0.568。
肩検出は直ったが、**投影の整列が 5 点中 4 点でしか合わない**（downtown は 5/5）。
相似変換が不安定になり、鼻と口に滲みが出る。この写真は目の間隔が 69px しかなく
（downtown は 99px）、3.09 倍に拡大する必要があるのも効いている。

**素材を替えるだけでは解決しない。** 整列を面外回転に強くするか、
5 点より密なランドマークで合わせる必要がある。

### 工程11: 自動QA を追加

`export_vrm.py` の検証は「必須ボーンが割り当たっているか」「スキンが存在するか」
までしか見ない。**骨を回したときの変形**と**浮遊片**は見ていなかったため、
§28・§29・§33 の欠陥をいずれも通していた。`_qa` で毎回確かめるようにした:

1. `pose_check.py` で arms / neck / all を当て、**実際に変形するか**を確認
2. `mesh_report.py` で最終メッシュの静的解析
3. 顔投影の整列 inliers が 5 未満なら警告（滲みの予兆）

門番ではなく点検なので、警告が出ても成果物は出す。

### 顔テクスチャ: 4096 にしても情報は増えない

顔メッシュは単独で焼くのでアトラス全体が顔＋肩になる。まず頭部だけで 2048 → 4096:

| ベイク | ArcFace | サイズ |
|---|---|---|
| 2048 | 0.6552 | 7.49MB |
| 4096 | 0.6529 | 13.32MB |

**ArcFace は横ばい。** 上限は元写真の顔（205px）であってベイク解像度ではない。
それでも「リサンプルが素直になるぶん眉と肌の粒が締まる」と考えて顔側だけ 4096 にし、
フルパイプラインを回した。**結果は下がった。**

| 実行 | ベイク | 正面 ArcFace |
|---|---|---|
| c2cc661c93e3 | 2048 | **0.7082** |
| 1ade66ec5e48 | 4096 | 0.6872 |
| f0437c610447 | 2048 | 0.6975 |

同一レンダ条件で測り直した値。**2048 どうしで 0.011 ばらつく**ので、4096 の
0.6872 はその振れ幅とほぼ重なる — 有意に悪いとは言えないが、**良い証拠は
2 回の測定でどちらも出なかった**。得るものが無くサイズだけ 15MB → 21MB
増えるので **2048 に戻した**。

ここで分かったより重要なこと: **同じ入力・同じ設定でも正面 ArcFace は
0.011 ばらつく。** TRELLIS のサンプラが確率的なので当然だが、これを知らずに
1 回ずつ測って比べると、0.01 程度の差はすべて誤読になる。以後この規模の
差を主張するときは複数回まわす。配布物は実測で最良だった c2cc661c93e3
（0.7082）に戻し、追加した工程11のポーズ検査も通ることを確認済み
（arms 0.4945 / neck 0.0364）。

## 36. KEHAI に載せて分かった、リグテンプレート由来の同乗物

Subject A のモデルを KEHAI にプリセットとして追加するにあたって現物を解析したところ、
**autorig の出力を見ただけでは気づかない欠陥が5つ**あった。いずれもテンプレート
（`.env` の `RIG_TEMPLATE_VRM` = VRoid サンプル）の VRM 拡張が、アーマチュアと一緒に

### 1. meta が pixiv 名義。ライセンス条項も丸ごとテンプレートのもの

avatarPermission: everyone   commercialUsage: corporation   allowRedistribution: true
modification: allowModificationRedistribution
allowExcessivelySexualUsage: true      allowPoliticalOrReligiousUsage: true

**なぜ設定されていなかったか**: `export_vrm.py:367-373` に meta を書くコードはあるが、
パイプラインは `autorig.py:457` の出力をコピーするだけで、そのコードを通っていなかった。
`export_vrm.py` は `--dry-run` の検証にしか使われていない。

### 2. サムネイルがテンプレートのアニメキャラの顔（1.2MB）

`meta.thumbnailImage` がテンプレート由来の画像を指したままだった。VRM を一覧表示する
ツールでは、この別人のイラストが本人として出る。実物のレンダから作った顔に差し替えた。

### 3. 目ボーンが顔の下半分を掴んでいた

| ボーン | 効いている頂点数 | 範囲 |
|---|---|---|
| `leftEye` (J_Adj_L_FaceEye) | **12,267** | 頭頂から11〜28cm・幅16cm |
| `rightEye` | **8,561** | 頭頂から13〜28cm・幅19cm |

### 4. spring bone が22本入っていた（「未設定」と書いてあったのに）

`autorig.py:14` と README は「髪・スカートの揺れもの(spring bone)は設定しない」と

いて揺らすべき別メッシュが無いので、物理を回すとズボンが布のように揺れる。拡張ごと削除した。

**コードのコメントが実物と食い違っていた例。** 「設定しない」は「自分では作らない」で
あって「入っていない」ではなかった。

### 5. モーフ0個 → KEHAI がアイドル動作の配線ごとスキップする

`vrm-viewer.tsx:4594` の `if (faceMeshes.length)` の中には、口パクだけでなく
**アイドルクリップ探索・`/motion/catalog` 取得・🎬ピッカーの表示・`idleEnabled` の初期化**
が入っている。`faceMeshes` は `morphTargetDictionary && morphTargetInfluences` が真の
メッシュだけなので、モーフ属性が皆無だと `undefined` になってこの塊が丸ごと飛ぶ。

顔メッシュに**変位ほぼゼロのスタブを1本**足すだけで通る。実体は sparse accessor

1頂点ぶん16バイトしか増えない）。全ゼロにするとビューア側の未使用モーフ削除
(`vrm-optimize.ts`) に消されるので 0.1mm だけ動かしてある。

実ブラウザで確認: 両プリミティブに `_kehai_stub` が乗り、🎬ピッカーが出て、
`[VRM] idle library: 3 clips for subject_a_v2_001` まで到達した。

### KEHAI 側で1つだけコードを直した — トゥーン処理の判定

`plainStyle`（ミク用のトゥーン／輪郭線／紫グレードを外す）は **`.glb`（VRM拡張なし）

## 37. ポーズを付けると袖が裂けて手が潰れる — 原因は3つ重なっていた

KEHAI 上でジェスチャーが付いた状態を見て「服と手が壊れている」と指摘された。
静止（T ポーズ）では問題が見えず、**骨を回したときだけ**出る。

`pose_check.py` と同じ軸（上腕 Z −55°、肘 Y −55°）でポーズを当て、辺が
静止時の何倍に伸びるかを数えて切り分けた。伸び3倍超の辺の分布:

| | 上腕 | 肩・胸 | 頭・髪 | 前腕〜手 | 合計 |
|---|---|---|---|---|---|
| 修正前 | 699 | 658 | 381 | 7 | **1768** |
| 腕フィット後 | 426 | 672 | 427 | 5 | 1574 |
| ＋衣装ボーン除外 | 426 | 672 | 427 | 5 | 1574 |
| ＋平滑化 48 | 359 | 402 | 350 | 7 | **1140** |

### 原因1: テンプレートの腕が身長比で15%短い

| | 腕を広げた幅 | 身長 | 比 |
|---|---|---|---|
| VRoid テンプレート | 1.389m | 1.615m | 0.860 |
| image-to-3D の T ポーズ | 1.577m | 1.600m | **0.986** |

ヒトの腕を広げた幅はおおむね身長に等しいので、**image-to-3D の出力の方が
解剖学的に正しく、テンプレートが短い**。`fit_armature` は身長だけで相似
スケールするので（コメントに「腕幅は身長比でおおむね決まる」と明記されていた）、
腕の骨が丸ごと約10cm内側に寄り、指の骨の塊が前腕の上に乗った。

自動ウェイトの結果（区間ごとの支配骨）:

| メッシュの部位 | 修正前 | 修正後 |
|---|---|---|
| 肘〜前腕 | Hand 18%, Roll_Hand 21% | LowerArm 25%, Roll_Elbow 25% |
| 前腕の先 | Hand 22%, **Little1** 13% | LowerArm 25%, Roll_LowerArm 25% |
| 手首 | **Index3 15%, Middle3 13%**（指先の骨） | Thumb1 20%, LowerArm 18% |
| 手のひら | **Middle3_end 20%** | Index1 25%, Hand 16% |
| 指先 | **Roll_Hand 53%, LowerArm 35%** | Index1 25%, Middle2 21% |

指先の骨が手首と手のひらを振り回し、指先は前腕の骨で動いていた。
`fit_arms()` を追加し、肩関節を支点に腕の骨の X 座標を k 倍する（この個体で k=1.174）。

### 原因2: テンプレートの衣装用ボーンが体の64%を握っていた

VRoid のリグは二次ボーン `J_Sec_*` を83本持つ。内訳は **Hair 59 / Tops 20 / Bust 4**。
Tops はトップスのパネル用で、**衣装が独立メッシュであること**が前提の骨。

image-to-3D の出力は衣服が体のシルエットに焼き込まれた単一メッシュなので、
対応する衣装が存在しない。それでも自動ウェイトは候補に含め、実測で

- モデル全体のウェイトの **64.2%** が `J_Sec_*`
- 肩の頂点の **78.7%** が 0.5 超

腕を回すと肩と上腕が「別キャラのトップス用ボーン」に従い、赤い板が飛び出す。
`use_deform=False` で候補から外した（骨も階層も残るので VRM 出力は壊れない）。

> **Hair まで外してはいけない。** 最初 `J_Sec_` を全部外したところ、顔の頂点が
> 拠り所を失って上腕ボーンに拾われ（顔上部で R_UpperArm 14%、顔下部で L_UpperArm 12%）、
> 腕を回すと**顔が溶けた**。髪の骨は頭の子なので頭と一緒に動き、顔を保持する
> 役として機能している。除外は Tops/Bottoms/Skirt/Coat だけにする。

### 原因3: エンベロープのウェイトの平滑化が足りない

`ARMATURE_AUTO`（heat map）はこのメッシュでウェイト0本を返すので
`ARMATURE_ENVELOPE` に落ちる（§28）。エンベロープは骨からの距離だけで決まるため
境界が階段状になり、曲げると裂ける。平滑化の回数を振ると:

| 回数 | 伸び3倍超の辺 | ポーズ変形量 |
|---|---|---|
| 8（旧既定） | 1574 | arms 0.4945 |
| 24 | 1276 | 0.4945 |
| **48（新既定）** | **1140** | 0.4945 |
| 96 | 1038 | 0.4945 |

48 でほぼ頭打ち。**どの値でも変形量は 0.4945 のまま**なので、なまり過ぎては
いない。`--weight-smooth` で上書きできる。

### ここまでで足りなかった — 1ポーズの試験に騙されていた

上の3つで「肘を曲げる」1ポーズの破断は 1768 → 1140 に減った。しかし KEHAI の実機で
見ると**まだボロボロ**だった。原因は試験の作り方で、実際のモーション（GestureLSM）は
全身の骨を同時に回す。**全身をランダムに回す負荷試験**に変えたら桁が違った:

| 破断（伸び3倍超の辺） | seed1 | seed2 | seed3 |
|---|---|---|---|
| 元の出荷物 | 8329 | 5794 | 7213 |
| 腕フィット＋衣装ボーン除外＋平滑化48 | 5458 | 3488 | 4342 |

内訳を見ると **88% が肩・胸と頭・髪**に集中していた（肩・胸 3522、頭・髪 1285）。

### エンベロープの限界 — 骨をどう選んでも減らない

テンプレートの**髪の骨が胸と肩のウェイトを持っていた**（VRoid では長い髪が肩に
かかるため）。髪の骨は頭の子なので、体を動かすと胸の頂点だけ頭に追従して裂ける。

ではと骨の除外を4通り試したが、**総量は動かなかった**:

| 追加で外した骨 | 破断(seed1) | 内訳の変化 |
|---|---|---|
| なし | 5458 | 肩・胸 3522 / 頭・髪 1285 |
| 髪 59本 | 6239 | 肩・胸 2095 / **頭・髪 3587** |
| ＋指 40本 | 5864 | 頭・髪 3709 |
| ＋Roll/Adj/_end | 5209 | 頭・髪 3072 |

**被害が肩から頭へ移るだけ。** 髪の骨を外すと顔の頂点が拠り所を失い、
エンベロープが上腕ボーンに割り当てて（顔上部で R_UpperArm 14%）顔が溶けた。

「メッシュの外にある骨を外す」規則も試したが、**内外判定自体ができなかった**。
レイの交差回数の偶奇はこのメッシュが非多様体（98,476本）で使えず、最近傍面の
法線を使う方法も法線が不整合で、核となる骨まで「外」と判定された。

heat map も駄目だった。骨を 167→43本まで減らしても代理メッシュ上で解けない
（`proxy_mode` は常に `ARMATURE_ENVELOPE`）。実測で**167本中130本がメッシュの外**に
浮いている（髪 59本中54、**指は40本中40本**）。

### 効いた方法 — テンプレートの手作りウェイトを近接転送する

エンベロープは「骨からの距離」でウェイトを決める。だから対応物のない骨が近くの面を
勝手に拾う。**VRoid のテンプレートは人が作ったウェイトを持っている**ので、そちらを
面の最近傍で引いてくれば「腕は腕から、胴は胴から」正しい配分が入る。
骨からの距離ではなく**人体のどこか**で決まるのが本質的な違い。

`_bind_via_template()` を `bind()` の最優先の経路にした。テンプレートのメッシュは
捨てずに残し、`fit_arms` の X 方向の引き伸ばしを骨と同じだけメッシュにも適用してから
（でないとこちらの前腕に向こうの手が当たる）`data_transfer` で転送する。

| 破断（伸び3倍超の辺） | seed1 | seed2 | seed3 |
|---|---|---|---|
| 元の出荷物 | 8329 | 5794 | 7213 |
| エンベロープで最善を尽くした版 | 5458 | 3488 | 4342 |
| **テンプレートのウェイト転送** | **753** | **281** | **382** |

指を握る試験は **402本 → 2本**（最大伸び 21.2倍 → 3.4倍）。
ポーズ検査の変形量は 0.4945 のまま、正面 ArcFace も 0.7082 で変わらない。
別のモデル（stylized の全身入力）でも 112本で、この経路は素材を選ばない。

**転送元は転送後に必ず破棄すること。** 残すと成果物に同梱されて 15MB → 55MB になる。

### 残っている限界

破断はゼロではない（seed1 で 753本、肩・胸に 374本）。肩は腕の回転と胴の境目で、
テンプレートと体型が違うほど残る。UniRig を入れれば根本的に解決する見込み。

### 途中で踏んだ落とし穴

- **最初に当てたテストポーズが間違っていた。** 肘を X 軸（＝骨の軸まわり＝ねじり）
  で 70° 回していたため、袖がキャンディラップ状に潰れた。これを「破断」と
  読み違えて原因を探しかけた。`pose_check.py` の POSES は肘を **Y 軸**で曲げる。
  ポーズを自作するときは既存の定義に合わせること。
- **手のクローズアップが袖の内側からのレンダだった。** ボーン位置にカメラを
  置いて 0.3m しか離さなかったため、`doubleSided` の内側の面が「破片」に見えた。
  外から 0.75m 以上離して撮ること。
- **座標系を取り違えて「浮遊ゴミがある」と誤読した。** Blender は Z 上、glTF は
  Y 上。Blender 側で断面の「Z 幅」を出して 2.21m という値を見て debris と判断
  しかけたが、glTF 座標で数え直すと **|Z|>0.35 の頂点は0個**だった。

## 38. 気配の実姿勢を吸い出して初めて分かったこと

§37 の修正を入れても、KEHAI 実機では**まだ手が棘状に飛び散っていた**。
自作のテストポーズでは再現しなかったので、**ブラウザから実際の骨の回転を
吸い出して** Blender で再現した（Playwright + `window.__vrmScene`）。
これで初めて実機と同じ絵が出た。

### 私の指標が間違っていた

「全身をランダムに回して伸び3倍超の辺を数える」で最適化していたが、
実姿勢では**破断はわずか243本**。しかしそのうち37本が手にあり、
**小さな手の中の37本が、あの棘を作っていた**。総数で見ていると手の被害が
埋もれる。部位別に見ること。

### 実機が当てている回転

| 骨 | 静止からの回転 |
|---|---|
| J_Bip_R_Hand | **152.4°** |
| J_Bip_L_Hand | 146.6° |
| Index1 / Middle1 / Ring1 / Little1 | **120〜132°** |

`vrm-motion-player.ts` の AIM は `leftHand: ["L_Wrist","L_Middle1"]` と
`right: ["L_Index1","L_Pinky1"]` で手のひらの基準系を作り、SMPL-X の指の関節を
そのまま指の骨に流す。**指が割れていない塊の手をこの角度で折れば飛び散る。**

### 効いた対策: 指のウェイトを手にたたむ

`fold_to_core()` で指のウェイトを `J_Bip_*_Hand` に加算し、指の頂点グループを
消す。手は塊のまま手首の回転にだけ従う。指は動かなくなるが、
**動かない塊のほうが飛び散る塊より正しい**。実姿勢での手の破断 37 → 9。

### 髪メッシュを転送元から外す

テンプレート転送の元から `Hair` メッシュを除いた。テンプレートでは髪が肩や胸に
かかっているので、近接で引くとこちらの胸が「髪の骨」を持ってしまい、体を
動かすと胸だけ頭に追従して裂ける。頭・髪の破断 167 → 5。

### 広げるほど悪くなる — たたむ範囲の実測

「対応物のない骨は全部たためばよい」と考えて範囲を広げたが、**逆効果だった**:

| たたむ範囲 | 実姿勢の破断 | 見た目 |
|---|---|---|
| **指のみ（採用）** | **251** | いちばん良い |
| ＋衣装・末端（ひねり骨は残す） | 371 | 上腕に筋状の破れ |
| ＋手のひねり骨 | 269 | **肩から長い筋** |
| 全部（ひねり骨も）| 214 | 数字は最小だが**見た目は最悪** |

ひねり骨（`J_Roll_*`）をたたむと、腕のひねりが1関節に集中して上腕が裂ける。
KEHAI 側も「ひねり補助が無いと1関節でせん断する」と警告を出している。
**総数が最小の案が見た目最良とは限らない。** 必ず絵で確かめること。

### 残っている限界（正直に）

袖と肩は**まだ裂ける**。実姿勢で 251本、うち頭・髪 195・前腕 24・上腕 12。
原因は、テンプレート（VRoid）のウェイトが「衣装が独立メッシュで、専用の骨で
動く」前提で作られていること。こちらのジャケットは体に溶接された一枚なので、
腕が 90〜150° 回ると袖のシェルが耐えられない。

**次の一手**: リグテンプレートを VRoid のサンプルから、KEHAI にある Avaturn 製
`subject_a.glb`（実写体型・ジャケット姿・73ジョイントの Mixamo リグ）に替える。
体型も服装もこちらのメッシュにずっと近く、KEHAI 側には Mixamo→VRM humanoid の
対応表が既にある（`frontend-src/src/renderer/src/utils/glb-humanoid.ts`）。
当初の計画（Phase 4-2）が想定していた経路でもある。

### 手法メモ: 実機の姿勢を吸い出す

```
Playwright で KEHAI を開く → window.__vrmScene を走査して
全ボーンの local quaternion を取る → glTF の rest rotation との差分を
Blender の pose_bone に当てる
```
`scratchpad/capture_pose.mjs` + `applylive.py`。**自作のテストポーズは当てにならない。**
実際のモーションは全身を同時に、想定より大きな角度で回す。

## 39. 顔トラックを FLAME に替える（着手・FLAME 取得待ち）

### なぜ替えるか

TRELLIS が作る頭は「**彫像**」で、目・口・顎という部品の概念がない。実測した
現状の欠陥（§36〜38）:

- 写真の**表情がそのまま固定**される。笑顔と細めた目が永久に消えない
- 目は平面に描かれた絵。眼球ジオメトリも瞼も無いので、**まばたきも視線も原理的に不可能**
- 口は歯も内側もない閉じた面。口パクも不可能
- 髪が蝋のように溶けた塊（3/4・横で最も目立つ）

**素材側の天井も測った。** `subject_a/` の全16枚で最大の顔は
`subject_face_downtown_1200.jpg` の **205px**（目間99px）。テクスチャの情報量は
ここで頭打ちで、ベイク解像度を上げても増えない（§35）。

| 写真 | 顔サイズ | 目間 |
|---|---|---|
| **subject_face_downtown_1200.jpg** | **205×281** | **99px** |
| subject_face_tweed_1200.jpg | 147×211 | 69px |
| subject_face_studio_600.jpg | 127×179 | 60px |
| subject-a.jpeg（当初）| 81×113 | 38px |

### なぜ MICA を選んだか

FLAME は眼球・顎・口内・表情基底を最初から持つパラメトリック頭部モデル。
1枚から当てる手法は複数あるが:

| 手法 | 向き | 判断 |
|---|---|---|
| **MICA** | 1枚 → **無表情の**同一人物 FLAME 形状 | **採用**。今回の目的そのもの |
| Pixel3DMM (2025) | 法線/UV 事前分布つきの詳細トラッキング | 幾何は上だが pytorch3d + nvdiffrast のソースビルドが要り、動画前提で過剰 |
| DECA / EMOCA / SMIRK | 表情つき再構成 | 表情を**捉えて**しまう。こちらは無表情が欲しい |

本人性はテクスチャ投影が担う（現状 ArcFace 0.707 は投影由来で、幾何ではない）。
だから幾何は「正しい部品構成の無表情な頭」であれば足りる。

## 40. 顔の超解像 — guidance を下げないと別人になる

公開されている素材の上限が顔 205px で、より大きい版は存在しない（§39）。そこで生成モデルで
拡大と質感付与を行うことにしたが、**これは情報を増やす処理ではなく作る処理**なので、
実在の人物では別人になりうる。NTIRE 2026 の実世界顔復元チャレンジが identity を
合否判定にしていて 10チーム中9チームしか通らなかったのも同じ問題。

`preprocessing/face_restore.py` を作り、RealVisXL V5.0 の img2img を顔の周りだけに当てた。
追加ダウンロードは不要（既に 6.5GB 導入済み）。

### まず測定の妥当性を確かめた

AI を使わない操作で ArcFace がどれだけ動くかを対照に取った:

| 操作 | ArcFace |
|---|---|
| 同じ画像を読み直す | 1.0000 |
| **Lanczos で 1.914倍に拡大** | **0.9920** |
| JPEG 品質70 で保存し直す | 0.9915 |
| 別セッションの実写（tweed） | 0.8569 |
| 別セッションの実写（studio） | 0.8064 |

**単純な拡大は同一性をほぼ完全に保つ。** つまりこの指標で落ちたら、それは解像度ではなく
**顔が変わった**ということ。同一人物を別の日に撮った写真どうしが 0.806〜0.857 なので、
そこが「本人と言える下限」の目安になる。

### guidance 5.0 では最弱でも別人になった

| strength | guidance | ArcFace | 目視 |
|---|---|---|---|
| 0.15 | 5.0 | **0.6115** | **明らかに別人**（顔幅・目・口が違う） |
| 0.25 | 5.0 | 0.4655 | 別人 |
| 0.35 | 5.0 | 0.3902 | 別人 |

**最も弱い 0.15 ですら、別セッションの実写（0.81〜0.86）より本人から遠い。**
SDXL の事前分布が「若く滑らかで整った顔」に強く引くためで、否定プロンプトでは止まらない。

### guidance を 2.0 に下げると成立する

| strength | guidance | ArcFace | 判定 |
|---|---|---|---|
| **0.05** | **2.0** | **0.8872** | **採用** |
| 0.08 | 2.0 | 0.8356 | 別セッション実写と同程度。際どい |
| 0.12 | 2.0 | 0.7856 | 下回る。不採用 |

guidance がプロンプトの「理想の顔」への引きの強さなので、ここを下げるのが効く。
strength だけ絞っても足りない。

目元を高倍率で比べると、0.05 でも **眉の毛が一本ずつ立ち、ほくろの輪郭が締まる**。
ただし額の細かい粒はやや均される。**効果は穏当**で、劇的に変わるわけではない。

### 実装した合否ゲート

既定を **strength 0.05 / guidance 2.0** とし、`--min-identity 0.85`（別セッション実写の
下限 0.806 に余裕を見た値）を下回ったら `meta["accepted"] = false` を返す。
呼び出し側はこれを見て、落ちていたら**元画像をそのまま使う**。

出力は 1200×800 → 2296×1531（顔 205px → 392px 相当）。

## 41. ICT-FaceKit の当て込み — 座標系と正則化で二度つまずいた

`preprocessing/ict_fit.py`。**写真からではなく、既にある TRELLIS 頭部に合わせる**。
その頭は実写由来で本人の形を持ち、正面 ArcFace 0.708 を出しているので、ICT の識別空間
（100個の線形 PCA）をその形に最も近くなるよう解けばよい。

手順は「正射投影で正面を撮る → 68点ランドマークを検出 → 画素から 3D に逆投影 →
相似変換と識別係数を交互に最小二乗」。正射投影を使うのは、**画素 →(X,Y) が一次式で
決まり、残る奥行きは光線を当てれば求まる**から。透視投影だと depth 無しでは戻せない。

### つまずき1: 座標系を三つ混ぜた

Blender は Z 上、glTF と ICT-FaceKit は Y 上。しかも **glTF インポータはメッシュデータ
自体を変換して読み込む**ので、Blender 内では Z 上になる。最初これを取り違えて:

- カメラが**頭頂**を向いた（顔ではなく髪と肩が写った）
- 直した後も、レンダのメタは Blender 座標なのに光線を当てる trimesh のメッシュは
  glTF 座標のままで、**顔が 0.2 ずれて頭が前方へ飛び出した**

**ICT-FaceKit も glTF も「Y上・+Z前」で同一規約**なので、`ortho_front.py` の側で
メタを glTF 座標に直して出すことにした。これで下流に変換が一切要らなくなる。
直後にランドマークの逆投影が 67/68 → **68/68** に改善した。

### つまずき2: 正則化がスケール不変でなかった

ICT は cm 単位（頭の高さ 33.8）だが対象は正規化されていて高さ 1.0。相似変換のスケールが
0.02 なので、基底を変換すると行列の要素が桁で小さくなる。そこに固定値の ridge を足すと
**係数がまったく動かない**（実測 alpha_norm 0.023、反復しても誤差が変わらなかった）。
`trace(AᵀA)/n` で正規化して解決。

### 正則化の強さ — 拘束は顔面にしか無い

`idx_to_fitting_verts` は顔面（7,801頂点）だけなので、弱いと**顔を合わせるために頭蓋が
後ろへ膨らむ**。実測:

| ridge | alpha_norm | 表面距離 | 幅 : 高 : 奥 |
|---|---|---|---|
| 0.05 | 55.2 | 0.00326 | 0.557 : 0.752 : **0.791** ← 対象全体より深い |
| 0.3 | 30.2 | 0.00290 | 0.506 : 0.764 : 0.750 |
| **1.0** | **20.6** | **0.00284** | 0.531 : 0.756 : 0.743 |
| 3.0 | 12.8 | 0.00293 | 0.527 : 0.722 : 0.663 |

**表面距離はほぼ横ばいで、変わるのは頭の比率だけ。** ならば係数の小さい方を採る。
1.0 を既定にした。

### 結果

- ランドマーク **68/68** 点が逆投影できた
- ランドマーク誤差 0.012 → 0.0103
- 表面距離 0.0112 → **0.00284**（対象の頭+肩が高さ1.0 なので、実寸およそ 1.3mm）
- 目視で、鼻・唇・顎の稜線と耳を持つ**解剖学的に正しい頭部**になっている

`--out-mesh` で確認用の obj を出せる。面とマテリアルの区切り（12個の `usemtl`）も
書き出すので、後段で「顔にだけ投影する」ために使える。

## 42. ICT 頭部にテクスチャを貼ると同一性が落ちる（未解決）

`blender/ict_head.py` で頭は組み上がり、53個の表情も動く（§43）。しかし実写を投影して
測ると、**正面 ArcFace 0.375〜0.394**。現行の TRELLIS 頭部は 0.708 なので大きく落ちる。

### 途中で潰した問題

**睫毛が目を覆っていた。** ICT の `M_EyeLashes` は本来アルファテクスチャ付きの薄板だが、
`.mtl` にアルファの指定はあってもテクスチャ画像は同梱されていない。不透明の黒で入れたら
目の上に黒い帯が乗り、**眼球が完全に隠れて ArcFace 0.168** まで落ちた。
アルファ前提の4パーツ（EyeLashes / EyeOcclusion / EyeBlend / LacrimalFluid）を
既定で外して 0.394 に回復。

**眼球への投影は効かなかった。** 眼球が無地で「死んだ目」になっているのが原因かと考えて
虹彩と強膜にも写真を投影したが、0.394 → 0.375 でむしろ微減。

### 残っている本質的な問題

投影自体は成功している（整列 inliers 5/5、回転 −0.04°）。肌の質感も皺も口も本人のもの。
それでも同一性が出ないのは、**幾何が本人と違う**からだと考えられる。

- 現行の TRELLIS 頭部は**彼女の写真から起こした形**なので、投影がそのまま噛み合う
- ICT は 4000スキャンの**100次元の線形 PCA**。表面距離 1.3mm まで寄せても、
  顔の比率までは再現しきれない
- `face_projection.py` の整列は**相似変換（回転・等方スケール・平行移動）だけ**で、
  比率の違いは吸収できない（せん断を入れると同一性が落ちると実測されている）

レンダを見ると、頭蓋が縦長の卵型で本人より細い。目も小さい。

### 次に試す価値がある方向

1. **ランドマークの重みを上げて再当て込み**。いまは表面距離を主に見ているが、
   ArcFace は目・鼻・口の位置で決まる。ランドマーク誤差 0.0103（実寸およそ4.5mm）を
   詰めれば効く可能性がある
2. **変形転写（deformation transfer）に切り替える**。ICT の幾何を使うのをやめ、
   **TRELLIS 頭部の形はそのまま残して 53個のブレンドシェイプだけを移す**。
   同一性 0.708 を保ったまま表情が動く。ただし眼球・歯のジオメトリは別途要る

## 43. 表情の変形転写 — 幾何を替えずに表情だけ借りる

§42 で ICT の幾何をそのまま使うと ArcFace 0.708 → 0.394 に落ちると分かった。そこで
**幾何は現行のまま残し、53個の表情差分だけを移植する**（`blender/transfer_expr.py`）。

`ict_fit.py` が当て込んだ ICT 素体は対象の表面に 1.3mm まで寄っているので、対象の各頂点に
ついて「ICT 表面上の最近傍点」を求め、その三角形の重心座標で差分を補間すればよい。

**結果は無損失だった。** 同一のレンダ条件での対照:

| | 正面 | 3/4 |
|---|---|---|
| 入力（表情なし） | 0.6617 | 0.5331 |
| **転写後（表情53個）** | **0.6617** | 0.5330 |

対応は 79,150頂点中 **22,294 が顔として採用**され、髪・肩・襟の 56,856 は距離で除外
（`near 0.012 / far 0.030` で滑らかに減衰。段差が出ないようにするため）。

口の中が空洞になる問題は、ICT の歯・歯茎・舌をそのまま持ち込んで解決した。歯は唇より
0.02 内側にあり、位置合わせは当て込みの結果をそのまま使える。

### 容量: 243MB → 19.8MB

VRM アドオンの書き出しは 243MB になった。3段階で削った:

| 手 | 効果 |
|---|---|
| モーフの法線・接線を除去 | KEHAI は位置しか駆動しない |
| **孤立した accessor を回収** | 法線を外しただけでは減らず、**154→197MB と増えた**。accessor が配列に残り、詰め直しが「まだ使われている」と判断してデータを持ち越していた |
| **全ゼロのモーフも sparse 化** | 最大の効果。結合すると体のプリミティブにも53本のターゲットが付くが中身は全部ゼロ。1本 2.4MB × 数十本で **62MB** を占めていた |

glTF は「同じメッシュの全プリミティブが同数のターゲットを持つこと」を要求するので、
ゼロのターゲットは消せない。最小の sparse（16バイト）に置き換える。

**実機で確認**: `[VRM] lip-sync morph: jawOpen`（以前は `no mouth-open morph found`）。
最終 VRM の正面 ArcFace 0.6960（従来 0.7082、実行ごとのゆらぎ 0.011 と同程度）。

### merge_head.py の修正

`bmesh.ops.bisect_plane` はシェイプキーのレイヤを持ち越さないので、表情を持つ頭を切ると
53個のモーフが消える。シェイプキーを持つオブジェクトは切らないようにした。
`bpy.ops.object.join()` はアクティブオブジェクトのシェイプキーを残すので、頭を
アクティブにする順序に変えた。

## 44. DiffLocks を動かすまでに潰した3つの壁

重み（9.7GB）は取得済みだったが、そのままでは動かなかった。

**壁1: flash_attn。** `attention.py` が無条件に import する。ビルドが要り CUDA と torch の
版に強く依存する。使い方は kv を束ねた通常の注意計算そのものなので、PyTorch 標準の
`scaled_dot_product_attention` で置き換えた。

**壁2: natten（近傍注意）。** ビルド済み配布が torch 2.5/cu124 向けに無く、ソースビルドも
失敗。近傍注意は「各クエリが周り k×k のキーだけを見る注意」なので索引操作で書ける。
本家の境界の扱い（端では窓を内側へずらし、どのクエリも必ず k² 個を見る）まで再現した。
**窓を全域にすると通常の注意と 1.3e-6 で一致することを確認**してある。
一度に (N,H,W,k²,nh,e) を作ると 128×128×49×1024 で 600MB を超えるので行方向に分割する。

**壁3: fallback の無い `exit(1)`。** ここが本命だった。`attention.py` のクロス注意は
flash_attn が無いと `print` して **`exit(1)` するだけ**で、例外も出さず無言で終了する。
`use_flash_2()` が flash_attn の有無を見ていたのが原因で、実際の計算は代替が引き受けるので
**可用性の判定から外した**。これで完走した。

生成物: **95,400本 × 256点の毛束**（293MB）。

## 45. 毛束をヘアカードにする

VRM は毛束を持てないので、アルファテクスチャを貼ったリボンに落とす
（`blender/hair_cards.py`）。既製の変換ツールは有料アドオンなので自作した。

毛束を根元の位置と「根元→毛先」の向きでクラスタリングし、クラスタごとに代表の毛筋に
沿ってリボンを張る。向きを特徴に入れるのは、同じ場所から前と後ろに分かれる毛を別の房
として扱うため。

### 位置合わせで二度外した

**大きさを重心からの平均距離で合わせたら 2.2倍に膨らみ、髪が頭を飲み込んだ。**
毛束の根元は頭皮の帽子状に分布し、対象側は顔まで含む塊なので、分布の形が違う。
**左右の幅**（どちらも「頭の横幅」を表す）で合わせるよう変えた。

**リボンの幅方向を毛筋自身の重心からのずれで決めたら、カードが平たく開いて円盤になった。**
毛が真下に垂れている房で向きが定まらないため。**頭の中心から外へ向かう向き**と接線の
外積に変えた。

現状 2,992枚（83,776頂点）。正面・3/4・横・後ろで髪として成立している。
残る課題は頭頂の隙間と、横から見たときの広がり。

## 46. 髪の統合と、UniRig が入らなかった理由

### 統合できたもの

DiffLocks の毛束 95,400本 → ヘアカード 3,976枚（111,328頂点）→ 本体に結合 → リギング →
VRM。**サイズは 522MB → 31.9MB**（sparse 化で 243MB 削減）。

| | 髪なし | **髪あり** |
|---|---|---|
| 正面 ArcFace | 0.6960 | **0.6895** |
| 3/4 ArcFace | — | 0.5677 |
| ポーズ変形 | 0.4873 | 0.4958 |
| サイズ | 19.8MB | 31.9MB |

実機で `[VRM] lip-sync morph: jawOpen` を確認。

### 頭頂の隙間 — 外積の退化だった

カードが頭頂で消えていた。原因は幅方向の決め方で、`cross(接線, 外向き)` を使っていたが
**つむじの周りは毛が外向きにそのまま伸びるので接線と外向きが平行**になり、外積が
ゼロに退化してカードが潰れる。別の軸で取り直すようにした。

なお残っている明るい部分は元テクスチャの日差しがカードの隙間から透けているもので、
地肌ではない。

### UniRig は**この環境では動かない**

MIT・登録不要・VRAM 8GB で条件は良かったが、skin モデルが
`flash_attn.modules.mha.MHA` を直接使う（skeleton 側の PTv3 は fallback を持つが
skin 側は無い）。そして:

| | |
|---|---|
| 公式のビルド済み wheel | **GLIBC 2.32 以上を要求** |
| このマシン | **GLIBC 2.31**（Ubuntu 20.04） |
| torch 2.6 / py3.10 向けの古い wheel | **存在しない** |
| ソースビルド | RAM 62GB中45GBを他サービスが使用、ディスク残 15GB で不可 |

DiffLocks では flash_attn を関数単位（`flash_attn_kvpacked_func` など）で SDPA に
置き換えられたが、UniRig が要求するのは **MHA モジュールそのもの**で、学習済みの
重み配置に合わせて再実装する必要があり、置換の難度が違う。

env と vendor は撤収した。**袖と肩の破断はテンプレート転写のまま残る**
（全身ランダムポーズで 753本、docs/05 §38）。

## 47. 「実際に動くか」の確認 — 低fpsが計測を壊していた話

配備した VRM が気配で本当に動くかを確認した。結論は**動く**。ただしそこに至るまでに、
**テスト環境のフレームレートが計測そのものを壊す**という問題を二度踏んだ。

### まず素の観測は失敗した

放置してまばたきを数えたが、90秒で **0回**（期待は20.5回）。だがこれは模型の不具合ではない。

ヘッドレス Chrome はソフトウェア描画（SwiftShader）で、38万頂点＋28MBテクスチャを
**1.12fps** でしか回せない。そして `blinkAmount()` はこう書かれている:

```
if (!blinking && now >= nextBlinkAt) { blinking = true; blinkT0 = now; }   // ← t=0、値は0
const t = (now - blinkT0) / BLINK_MS;                                      // BLINK_MS = 130
if (t >= 1) { blinking = false; ... }                                      // ← 次フレームは t=6.8
```

フレーム間隔が890msなので、まばたきは**必ず t=0（値0）で始まり、次に見たときには
既に t≥1 で終わっている**。山が一度も描かれない。この条件下では
**何回試しても 0 しか出ない** — 確率の問題ではなく構造的に捕捉できない。

### 直し方: シミュレーテッドクロック

気配には `?debug=1` と `__AI_DEBUG__.setTime(秒)` があり、**実fpsと切り離して**
1/60秒刻みで再生できる。まばたきは初期化から2500ms後に始まるので、その前後を狙撃した:

| シミュレーション時刻 | eyeBlinkLeft / Right |
|---|---|
| 2.400s | 0.000 |
| 2.520s | **0.256** |
| 2.565s | **0.769** |
| 2.620s | **0.205** |
| 2.750s | 0.000 |

山が出た。実行時に駆動されている。

### 感情も同じ罠にいた

`__vrmEmotion('sad')` で15個のモーフが動いた（browDown 0.21 / browInnerUp 0.10 /
mouthFrown 0.07 / noseSneer 0.08 …）。値が小さく見えるが、これも fps のせいで、
`emoLevel += (target - emoLevel) * 0.08` は**毎フレーム**なので
1.3fps×2.5秒＝約3フレームでは `1-0.92³ = 0.23` までしか上がらない。
実機の60fpsなら0.5秒で **0.92**。測定値は約4倍して読むべき下限値である。

### モーフ自体の検証は Blender でやるべきだった

ブラウザはカメラを毎フレーム自前で解き直すので固定できず、アイドル動作で体も揺れ、
画素差分が顔以外に汚染される。配備済み VRM を Blender でカメラ完全固定のまま描くと、
各モーフが**解剖学的に正しい領域だけ**を動かしていることが一目で出た:

| モーフ | 変化した領域（画像座標） | |
|---|---|---|
| jawOpen | y[302,511] | 口が開き**歯と舌が見える** |
| eyeBlinkLeft/Right | y[353,381]（28px帯） | 瞼だけ |
| browInnerUp | y[232,429] | 額と眉 |
| mouthFunnel | y[374,511] | 口 |

**教訓**: 幾何が正しいかはオフラインの固定カメラで、駆動が走るかは
シミュレーテッドクロックで見る。実時間のブラウザ画素差分はどちらの証拠にもならない。

## 48. 見た目の退行 — 髪カードの撤回と、肩の当て布

「見た目が絶望的、もはや人ではないかも」という指摘を受けて全身を素直な照明で描き直した。
指摘は正しく、**二つの欠陥**が出ていた。

### 髪カードは改悪だった。撤回した

素直な照明で並べると議論の余地がなかった:

| | 髪カードなし (19.8MB) | 髪カードあり (31.9MB) |
|---|---|---|
| 見え方 | ボブ。顔が見える。人に見える | 半透明の紐が顔にかかり、濡れた藁 |

拡大した質感（毛の筋・彩度）だけを見て「改善」と判断していたが、**全身の距離で見ると
別の話**だった。カードが疎で半透明なため、髪の量として読めない。配備を戻した。

**測り方の誤り**: 質感の局所指標（隣接画素差 1.88→3.01、彩度 24→46）は上がっていた。
だが見る人は顔の隣で髪の塊を見る。局所指標は全身の印象を代表しない。

### 肩の半透明の当て布 — 元からあり、私が広げた

頭の切り出しは襟と肩まで含んでいて、体のジャケットに食い込む。

| | 頭メッシュの下端 | 頂点数 |
|---|---|---|
| 元の版 (8/29) | z 1.301 | 65,266 |
| 表情を入れた版 | z **1.219** | 79,039 |

表情キーを守るため `cut_z` をシェイプキー持ちで飛ばしたのが原因。**元からある欠陥を
8cm 広げた**。

**直し方**: `bmesh.new()` + `to_mesh()` はシェイプキーのレイヤを落とすが、
**編集モードの `bmesh.from_edit_mesh()` は保つ**。これで切れる。

- 肩: z < 1.388（体の襟の上端が 1.39 なので切り口が隠れる）
- 襟: z < 1.445 かつ首の軸から 0.085m 超（写真の襟は左右非対称で平面では切れない）

**軸の取り方で一度失敗した。** 首の軸を頭側の頂点の平均で取ると、**襟の頂点に
引っ張られて 5cm 偏り**、片側の襟を残したまま反対側の首を削った。体側の首
（z 1.40〜1.42 で幅 0.13m、曖昧さがない）の中央値から取り直して解決。

25,805頂点を除去、シェイプキー 53個を保持、16.5MB。ポーズ変形 0.501、
まばたき 0.769、`jawOpen` すべて健在。

### Blender を通すと VRM 拡張が落ちる

glTF エクスポータは `VRMC_vrm` を知らないので、トリムのために一度 Blender を通すと
humanoid 定義ごと消える（`is_vrm: false`）。ノードの並びは変わるが**名前は保たれる**
（増えるのは Blender が足す "Armature" だけ）ので、名前で引き直して移植した
（52ボーン + 34モーフ束）。`scratchpad/graft_vrm.py`。

### 混入していないものを混入と誤認した

Blender で読むと 42頂点の `Icosphere` が現れ、身長が 2.645m になる。ファイルに
球が入っていると考えたが、**glTF のメッシュは `geometry_0.001` の1つだけ**だった。
VRM アドオンがインポート時に作る表示用の当たり判定で、three.js の KEHAI には無い。
KEHAI の紫のもやはアプリ自身の演出であって、模型の欠陥ではない。

## 49. 形式は制約ではなかった — KEHAI は .glb をそのまま読む

「VRM という制限があるから今の生成モデルを使っているのでは」という問いを受けて
KEHAI のコードを読み直した。**制限は無かった。**

`App.tsx` の振り分け:

| 形式 | 経路 |
|---|---|
| `.vrm` | three-vrm ビューア |
| **`.glb`** | **同じビューア。`utils/glb-humanoid.ts` が Mixamo 骨名の上に VRMHumanoid を組む** |
| `.pmx` | MMD ビューア |

`glb-humanoid.ts` のコメントにこうある — *"Ready Player Me, Avaturn and Character
Creator all ship it"*。そして**現行の `subject_a` プリセット自体が `.glb`** で、
VRM ですらない。

つまり **VRM 化は TRELLIS を使う理由ではない**。TRELLIS は「実在の人物を写真1枚から
起こす」ために使っていたのであって、出力形式とは無関係だった。外部のアバター生成器が
Mixamo 骨の GLB を吐くなら、**変換なしでそのまま置ける**。

### 手持ちの2体を並べると

| | subject_a (.glb / Avaturn) | V2 (.vrm / 自前) |
|---|---|---|
| 頂点 | 81,708 | 151,974 |
| マテリアル | 9（髪・服が独立） | 3（全部溶接） |
| ARKit 表情 | **最初からある**（162モーフ） | 53（移植した） |
| 見え方 | 服が服に、髪が髪に見える | フォトグラメトリの塊 |

V2 が勝っているのは顔テクスチャの本人らしさだけだった。

`scripts/check_kehai_model.py` を追加。外部で作ったモデルを置く前に、Mixamo 骨16本・
`eyeBlinkLeft/Right`・`jawOpen` の有無を検分する。

### 超解像した写真は本人から遠ざかっていた

MetaPerson に渡す1枚を選ぶため、手持ち16枚の ArcFace を測った。

| | ArcFace |
|---|---|
| 超解像 × 元にした写真 | 0.8790 |
| **超解像 × 他の実写** | **0.68〜0.70** |
