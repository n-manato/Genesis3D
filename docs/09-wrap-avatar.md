# ラップ方式 — 生成メッシュは測るために回し、出荷はテンプレートのトポロジ

`docs/08-game-avatar.md` の続き。**接合をやめてラップにした**記録。

## 1. なぜ変えたか

接合方式（`scripts/gen_game_avatar.py`）は「生成した頭」を出荷物にして、テンプレートの
体に繋いでいた。KEHAI で動かしたときに2つの欠陥が見えたので原因を測った
（`jobs/ga_v2_005/scores/merge.json`）:

```
applied_scale : 0.31479     ← head-width 基準。これが黙って採用されていた
scale_by_span : 0.45527     ← 44.6% 違う
merged height : 1.52286     ← 指定は 1.60m。7.7cm 足りない
head_max_width: 0.52162     ← 高さ1.0の頭で最大幅0.52。髪か肩を拾っている
```

**頭が正しい寸法の 69% に縮んで胴に付いていた。** 首が長く見えた原因はこれ。

根本の問題は「2つのランドマーク比のどちらを信じるか」を決める根拠が無いこと。
head-width 基準が正当化できたのは頭と体が同一人物由来だったときだけで、体が
他人のテンプレートになった時点でどちらの比も根拠を失っていた。

もう1つの欠陥（顔の黒い斑点）は削減が原因だった: 682,766 → 179,527頂点（比 0.146）。
COLLAPSE は髪のような細い構造で退化面と法線反転を作る。

**どちらもモデルの問題ではなく、生成メッシュを出荷物にしたがゆえの後処理の問題。**

## 2. 3回のアプローチの共通点

| | held-out ArcFace | リグ | 壊れた場所 |
|---|---|---|---|
| 旧 pipeline（全身生成） | 0.774 | 指が死ぬ・肩が破断 | 毎回トポロジが違う |
| game_avatar v1（テンプレ変形） | 0.451 | 完璧 | PCA 事前分布の天井 |
| game_avatar v2（頭生成＋体テンプレ） | 0.62〜0.70 | 体は完璧 | 接合部 |

3回とも**生成メッシュを出荷物にして後から修理**していた。修理の工程（削減・接合・
ウェイト転送・モーフ転写）が欠陥の発生源になっていた。

## 3. 反転

**生成は測るために回し、出荷するのはテンプレートのトポロジ。**

手段は非剛体 ICP（ラップ）。テンプレートの頭を生成された頭の表面に吸着させる。

```
写真 → TRELLIS で頭を生成（出荷しない・削減もしない）
                    ↓
      テンプレートの頭を非剛体ICPで吸着 → テンプレートを変形 → 体型を寄せる → 投影
```

v1 の RBF との違いは**拘束の密度**。v1 は 68点しか無く頂点は平均 4.7mm しか動かず、
テンプレートの頭は依然として別人の頭だった。ラップは 688点の面対応があり、
顔面の残差 1.691mm まで合う。

## 5. アルゴリズム（Amberg et al. 2007, Optimal Step Nonrigid ICP）

頂点ごとに 3x4 のアフィン X_i を置き、疎な最小二乗で解く:

```
E = Σ w_i |X_i [v_i;1] - u_i|²        データ項（u_i は対象表面の最近点）
  + α Σ_(i,j)∈E |(X_i - X_j) G|²      剛性項（G = diag(1,1,1,γ)）
  + β Σ |X_i [v_i;1] - l_i|²          ランドマーク項
  + λ_i |X_i - I|²                     ダンピング項（顔マスクの外ほど強く）
```

α を 200 → 0.5 へ焼きなます。実装は `preprocessing/wrap_head.py`。
変形の適用は既存の `preprocessing/shape_transfer.py`（glTF 直接手術・無損失検証済み）に
`{"centers", "targets"}` を渡すだけで済む。**Blender を一度も通さない。**

## 6. 踏んだ罠と、それぞれの証拠

### 6.1 アフィンを増分として解いた（68点残差が反復ごとに増えた）

Amberg のアフィンは**常に元の頂点 v0 に対して**解く。私は `x = aff·[x;1]` と増分で
適用しつつ、ランドマーク項だけ v0 基準にしていた。両者が競合した:

```
増分（誤り）: 68点 RMS  20.988 → 39.156mm   ← 反復のたびに悪化
標準形（正）: 68点 RMS  20.988 →  2.874mm
```

増分にすると剛性項が罰するのは「増分どうしの差」だけで、累積した変形は
何も正則化されない。

### 6.2 対象の面法線は信用できない（棄却の 63〜68% が法線）

TRELLIS の出力を trimesh で見ると:

```
外向きの面      51.7%          ← 偶然と同じ
is_watertight   False
境界辺          130,409本       ← 三角形スープ
fix_normals()   効果なし（51.7% のまま）
fix_winding()   効果なし
```

法線テストの目的は「面に斜めから当たった対応を捨てる」ことなので、**符号を見ずに
絶対値で足りる**。切り替えで対応が 512 → 1020点に増えた。

### 6.3 顔マスクを距離で切ると頭皮が髪に吸着する

頭は高さ 374mm しかないので、68点からの半径 95mm でも**頭の 79%**（1,752頂点中1,387）
が候補に入る。対象は TRELLIS が生成した**髪付き**の頭なので、頭皮が髪の表面に
吸着して頭蓋が膨らむ。

正しい境界は 68点が張る輪郭そのもの。**正面から見た XY 凸包の内側 ＋ 前を向いた面**に
変えて 1,387 → 936点。XY 凸包だけでは後頭部も同じ足元に射影されるので、法線で
表裏を分ける必要がある。

### 6.4 逆投影した68点に粗大な外れ値がある（最小二乗の位置合わせは使えない）

点ごとの残差（全68点で合わせた場合）: **#4 が 219mm、#47 が 192mm**。
部分集合ごとに解くとスケール推定が桁で暴れた:

| 使った点 | スケール | 中央27-67の残差 |
|---|---|---|
| 全68 | 0.4346 | 22.3mm |
| 輪郭0-16 | 0.5852 | 66.1mm |
| 目36-47 | **0.1175** | 52.3mm |
| 鼻27-35 | 0.5798 | **14.2mm** |

残差の中央絶対偏差で切りながら解き直す（`robust_umeyama`）ことで:

```
初期残差 44.33mm → 9.14mm    採用 53/68点  スケール 0.4346 → 0.5948
```

### 6.5 額は前髪に覆われるのでデータ項に入れてはいけない

修正前は額の頂点が **152.54mm** 動いて髪の表面に貼り付いた（頭の高さは 374mm）。
しかも最初の反復の許容距離が広いので、一度貼り付くと以降の反復では戻らない。

眉の上端から 15mm で重みを 0 に落とす（`--brow-cap`）。観測できない領域は剛性項に
任せる ——「証拠が無いなら動かさない」。

### 6.6 データ項の無い領域はアフィンの外挿で暴れる

剛性項が罰するのは「隣どうしのアフィンの差」だけで、同じアフィンでも適用する点が
遠ければ変位は大きくなる。顔で解いた回転・スケールが後頭部に外挿されて
**最大 260mm** 動いた。ダンピング項 `λ_i |X_i - I|²` で「証拠の無い領域は
テンプレートの形のまま」という事前分布を入れた。

### 6.7 密な中心の厳密 RBF 補間は場が振動する（法線とモーフが壊れる）

ラップの結果（テンプレの頭 1,752頂点ぶんの対応）をそのまま `shape_transfer` の
RBF 中心にすると、**位置は正確に出るのに法線とモーフ差分が壊れる**。

`shape_transfer` は残差 5.30e-13 と報告する（中心では厳密補間だから当然）。
壊れているのは**中心の間**:

```
中心の最近傍間隔     最小 0.125mm（中央 5.31mm）
(I+J) の特異値       最大 91.59 / 最小 0.00      ← 局所的に91倍伸びと退化
|f(x+d)-f(x)|/|d|    最大 21.8（中央 0.151、90% 1.19）
```

モーフ差分は `d' = d + f(x+d) - f(x)` で送るので、この振動がそのまま振幅に乗る:

| モーフ | 素テンプレ | 間引き無し | **間引き 2mm** |
|---|---|---|---|
| ou | 4.62mm | 13.60mm (**2.94x**) | 7.58mm (1.64x) |
| mouthSmileLeft | 4.55mm | 11.89mm (**2.61x**) | 6.96mm (1.53x) |
| ih | 7.17mm | 9.60mm (1.34x) | 12.85mm (1.79x) |
| mouthFunnel | 9.47mm | 14.95mm (1.58x) | 14.05mm (1.48x) |
| jawOpen | 17.24mm | 21.32mm (1.24x) | 20.98mm (1.22x) |
| eyeBlinkLeft | 9.73mm | 12.51mm (1.29x) | 9.17mm (**0.94x**) |
| browDownLeft | 4.71mm | 4.23mm (0.90x) | 4.38mm (0.93x) |
| **比の最大** | | **2.94x** | **1.79x** |

間引きで比の最大が 2.94 → 1.79倍に落ち、まばたきは 0.94倍とほぼ原寸に戻った。
**まだ 1.5〜1.8倍が残る**（σmax 5.75 のぶん）。振幅の小さい口のモーフに集中している。

**`--smooth` では直らない。悪化する。** ほぼ特異な行列に対角を足すため:

| | 位置誤差 平均/最大 | σmax |
|---|---|---|
| smooth 0 | 0.001 / 0.044mm | 91.59 |
| smooth 0.001 | **8.848 / 733.98mm** | 312.80 |
| smooth 0.01 | 23.446 / 273.54mm | 21.55 |

直るのは**中心の間隔を制御すること**（`thin_centers`）。外側から残す:

| 最小間隔 | 中心 | 顔面の位置誤差 | σmax |
|---|---|---|---|
| なし | 1,752 | 0.001mm | 91.59 |
| **2.0mm** | **1,540** | **0.443mm** | **5.75** |
| 3.0mm | 1,384 | 0.617mm | 5.04 |
| 6.0mm | 1,022 | 0.998mm | 3.53 |

既定は 2.0mm。顔面の位置を 0.44mm 諦めて条件数を 16分の1にする取り引き。

**より正しい直し方は残してある**: 頭の頂点位置は NICP が全部持っているので RBF で
補間する必要がなく、モーフと法線は**一輪近傍から求めた局所アフィン**
（Sumner & Popović の変形転写）で送れば大域 RBF の条件数問題が消える。
`shape_transfer.deform()` の中核に手を入れることになるので、体の経路
（無損失を検証済み）を壊さない形での実装は未着手。

### 6.8 眼球のジオメトリを顔面に吸着させていた（同一性が 0.05 落ちていた）

レンダの目の周りに**金属質の裂けた筋**が出ていた。当初これを「テンプレートの
まつ毛カードが写真の目とずれている」と診断したが、**誤りだった。** マテリアルを
色分けして描くと（head=緑 / body=青 / opacity=マゼンタ）、目の位置に `opacity`
プリミティブは無い。

実体は**眼球が瞼の面まで引き出されて相互貫入していた**こと。眼球は
前を向いていて 68点の XY 凸包の内側にあるので、法線ゲートと凸包だけでは
データ項から落ちない。

`texture_processing/face_texture_blend.py` で書いた可視性判定を、ラップの
顔マスクにも掛けた（`--visibility`、既定で有効）。カメラから各頂点へ光線を
飛ばし、最初に当たるのがその頂点自身かを見る。実測 898/1752頂点が可視。

| | バスト tweed | 全身 tweed |
|---|---|---|
| 可視性ゲート無し | 0.6234 | 0.5923 |
| **可視性ゲート有り** | **0.6700** | **0.6319** |

顔の残差も 3.285 → 1.961mm に改善した。**+0.047 / +0.040 は単一の変更としては
このプロジェクトで最大の改善。**

### 6.9 溶接は必須

UV の切れ目でテンプレートは頂点を重複して持つ（1,921 → 溶接後 1,752）。
重複を別々に解くと継ぎ目が割れ、さらに **RBF の中心が同一点になって行列が特異**になる。

## 7. 測定の訂正 — studio は held-out ではなかった

`scripts/measure_identity.py` を作って参照どうしの類似度も出したところ:

```
subject_face_studio_600  vs  subject-a_head_1024（テクスチャの由来）  = 0.9773
subject_face_tweed_head  vs  subject-a_head_1024                      = 0.8034
subject_face_tweed_head  vs  subject_face_studio_600                       = 0.8184
```

**studio は由来写真と同一セッション**で、held-out になっていない。docs/08 までの
「tweed / studio 基準」の数値のうち studio 側は同一性の指標として弱い。
以降は **tweed のみを held-out の主指標**にする。

| ラップ（対象=削減済み） | 273 | 0.6158 | 48 | **0.6098** |

- **全身が主用途（モーション）で、そこは +0.05〜0.08 改善。** 接合方式は頭が 69% に

黒い斑点と、顎の下に平らな継ぎ目のパッチ、極端に長い首）。指標だけで判断しないこと。

## 9. 剛性の下限の掃引 — 残差を最小化すると同一性が落ちる

対象は未削減 `head_clean.glb`。他の条件は同一。

| 下限 α | 顔面変位 平均/最大 | 顔面の残差 | **バスト tweed** | **全身 tweed** |
|---|---|---|---|---|
| 5.0 | 2.88 / 8.97mm | 大 | 0.5738 | 0.5644 |
| **2.0** | 4.03 / 14.18mm | 中 | **0.6208** | **0.5994** |
| 0.5 | 5.88 / 29.89mm | **1.691mm（最小）** | 0.5804 | 0.5933 |
| （接合 v2 の参考値） | — | — | 0.6189 | 0.5329 |

**非単調。** 硬すぎると対象に当たらず、緩すぎると TRELLIS の高周波を 1,752頂点が
追ってしまう。下限 2.0 が最適で、**そこでは接合方式を両方の指標で上回る**。

幾何の残差が最小になるのは下限 0.5 だが、そこは同一性が 0.04 低い。
**幾何の残差を目的関数にしてはいけない。** 既定値を 2.0 に変更した。

## 10. 効かなかった試み — テクスチャ側の2つ

**どちらも道具は残してあるが、パイプラインには入れていない。** 効果を測ってから
入れるという §9 の教訓をここでも適用した。

### 10.1 遮蔽を見ない投影（真の不具合だが、直すと悪化した）

`blender/project_face.py` は写真をカメラから投影して焼くが、**遮蔽を見ていない**
（facing-dot の重みだけ）。眼球・歯・口内は前を向いているので判定を通り、瞼と唇の
裏にあるのに写真が焼き込まれる。UV を見ると確かに眼球・歯の島が写真で塗り潰されていた。

`texture_processing/face_texture_blend.py` を書いて直した。カメラから各三角形の
重心へ光線を飛ばし、最初に当たるのがその三角形かを見る（実測: 3,434枚のうち
見える 2,099 / 隠れている 1,335）。遮蔽元の内訳も取れる:

    head 1,306   後頭部が前頭部に隠れているだけ
    body     16
    opacity  13   髪カードの裏の肌

機構は正しく動いた（眼球と歯がテンプレートの絵に戻った）。**しかし見た目は悪化した。**

- 写真は笑って目が細まっているのに、テンプレートの眼球は開いている。両方が出ると
  驚いた顔になる。**必要なのはテクスチャの合成ではなく、目の開閉状態の一致**
- 額のマスク外の部分でテンプレートの肌に戻り、写真に写っていた前髪が消えて
  生え際が失われた

### 10.2 髪色の転写（届く範囲が足りない）

`texture_processing/hair_color.py`。Reinhard の色転写（Lab で平均と標準偏差を合わせる）で
テンプレートの金髪を写真の髪色に寄せる。写真の髪画素は「眉より上、かつ背景を除き、
かつ顔の内側から採った肌色から遠い」で集める（実測 212,423画素）。

`opacity`（髪カード 680頂点）は色が変わった。**が、頭頂の頭皮が金髪のまま残る。**
頭皮は `head` マテリアル側にあり、投影した写真の枠（顔に合わせた 1.35倍）の外なので
テンプレートの絵が残る。幾何で切ろうとしたが、

- 「髪カードの裏の肌」で定義 → **13枚しか無かった**（テンプレの髪は後ろで束ねてあり、
  頭頂に髪カードが無い）
- 相対高さ（眉より上 = 頭の高さの 0.72 より上）で定義 → 範囲は取れたが、
  頭頂の可視領域は投影の枠外なので色を変えても最終レンダに反映されなかった

さらに `opacity` にはまつ毛のカードも入っており、髪色（ほぼ無彩色）にすると
**目の上に灰色の塊が乗る**。髪とまつ毛は分けて扱う必要がある。

**まつ毛のカードそのものが新たに特定した欠陥。** ラップ後はテンプレートの目の位置に
合わせたカードが写真の目とずれる。写真にはまつ毛が写っているのでカードは冗長。

身長 1.5997m（指定 1.60m・誤差 0.3mm）   足元の y = -0.0042

## 13. 髪・まつ毛・服・モーフ振幅（4項目）

### 13.1 モーフ振幅 — 局所アフィン（Sumner & Popovic）

大域 RBF のヤコビアン（§6.7）を、**一輪近傍から解いた変形勾配**に置き換えた
（`shape_transfer.local_affines`）。位置は変わらない。全175モーフ中、差分が
有意な98個の振幅比:

| モード | σ最小/最大 | 比 中央 | 90% | 最大 | 2倍超 |
|---|---|---|---|---|---|
| RBF の場 | 0.0026 / 3.263 | 1.103 | 1.821 | 2.470 | 4個 |
| 局所 clamp 2.5 | 0.400 / 2.500 | 1.489 | 2.025 | 2.473 | 12個 |
| **局所 clamp 1.5** | 0.667 / 1.500 | **1.141** | **1.393** | **1.494** | **0個** |

**既知アフィンでの検証では場モードのほうが厳密**（誤差 4.6e-10 対 3.0e-04 m）。
差は一輪が退化した頂点で局所アフィンが恒等に落ちるぶんで、これは安全側の
意図した挙動（eps を変えても不変なのがその証拠）。

同一性は バスト 0.6700 → 0.6558、全身 0.6319 → 0.6361。**バストで 0.014 の
取り引き**を、モーフの健全性（KEHAI は175個を駆動する）と引き換えに受けた。

### 13.1b 最終の積み上げ（held-out ArcFace / tweed 基準）

| 変更 | バスト | 全身 |
|---|---|---|
| 接合方式（`ga_v2_005`） | 0.6189 | 0.5329 |
| ラップ初版（`gw_002`） | 0.6234 | 0.5923 |
| ＋可視性ゲート（§6.8） | 0.6700 | 0.6319 |
| ＋局所アフィン clamp1.5（§13.1） | 0.6558 | 0.6361 |
| ＋投影の facing 下限 0.15→0.01 | 0.6637 | 0.6426 |
| ＋髪の色転写（生え際は局所SD・§13.2） | **0.6722** | **0.6544** |
| **＋服の色転写（`gw_004` 最終）** | **0.6629** | **0.6470** |

服の色転写でバストが 0.009 下がるのは、顔の周囲の文脈（襟の色）が変わって
ArcFace の切り出しがずれるため。**接合方式に対して バスト +0.044 / 全身 +0.114。**

### 13.2 髪 — テクスチャの色転写

**Rocketbox には髪のボリュームを持つジオメトリが無い。** マテリアルを色分けして
描くと頭は禿げていて、髪は `head` テクスチャの頭皮に描いた絵＋`opacity` の
アルファカード（ポニーテール）でできている。だから**髪型は寄せられない。色だけ**。

頭頂に投影が届かない理由も測れた: 頭頂の法線は上向きで、`project_face.py` の
`--facing-min 0.15` に届かないので投影の重みがほぼ0になり、テンプレートの絵が残る。

`texture_processing/hair_color.py`（Reinhard の色転写）＋
`face_texture_blend.py` のマスク生成で、頭皮と髪カードに色を移す。

| | バスト tweed | 全身 tweed |
|---|---|---|
| 髪の色替え無し | 0.6558 | 0.6361 |
| **頭皮のみ** | **0.6625** | **0.6511** |
| 頭皮＋髪カード | 0.6548 | 0.6389 |
| （髪カードのアルファを落とした場合） | 0.5609 | 0.5763 |

**頭皮の色替えは同一性を上げる**（本人は黒髪なので）。髪カードも入れると
0.01 下がるが、頭頂だけ黒くしてポニーテールが金髪のままだと見た目が破綻するので
両方入れる。0.01 は実行間のばらつきの範囲。

**生え際は高さの閾値では決まらない。** 平面で切ると水泳帽のような水平な境界が出た
（閾値 0.78 / 0.82 / 0.86 を掃引して全部そうなった）。テンプレートのテクスチャは
**描かれた生え際**を持っているので、毛束の高周波成分でそれを拾う。局所標準偏差の実測:

    頬 0.83   額 1.76   鼻先 3.46   側頭 4.30   頭頂 13.45

眉より上の帯と論理積を取り、閾値 3.0 で曲線の生え際が得られる（`--hair-detail-sd`）。

投影の `--facing-min` も 0.15 → 0.01 に下げた。頭頂は法線が上向きで既定値では
写真が届かない。下げると バスト +0.008 / 全身 +0.007。斜めから当たる引き伸ばしは
顔ではなく髪と頭皮なので目立たない。

### 13.3 まつ毛 — 髪カードから分離する

`opacity` は髪カードと**まつ毛**の両方を持つ。テクスチャを丸ごと髪色（本人は
ほぼ無彩色の黒髪）にすると、**まつ毛カードが目の上に太い黒い眼線として乗る**。
目のランドマークから 30mm 以内の三角形をまつ毛とみなして除外する
（実測 髪カード 460 / まつ毛 208）。

### 13.4 服 — テクスチャの色転写（2Dの問題）

Rocketbox の服は**メッシュではなく `f001_body_color.tga`（2048²）に描いてある**ので、
衣装合わせは3Dのガーメントフィッティングではなく画像の色替えになる。

**色で服と肌を分けてはいけない。** テンプレートのシャツはピンク [188,104,116] で
肌 [205,151,137] とほぼ区別が付かない。幾何（高さと中心からの距離）で切る。

`texture_processing/garment_color.py`。実測（`subject_tpose_front.png` は赤いブレザーと
黒いスラックス）:

| | 元 | 色替え後 | 狙い |
|---|---|---|---|
| シャツ | [188,103,115] ピンク | **[177, 30, 46]** | [172, 21, 40] |
| ズボン | [ 57, 79, 91] デニム | **[ 38, 38, 41]** | [ 32, 31, 35] |

上着の色は**中央を避けて左右の胸元から採る** ——ブレザーの前が開いていると
中央はインナーの色になる。

## 14. さらに踏んだ罠

### 14.1 UV の V を反転していた（マスクが全部ずれていた）

glTF のテクスチャ座標は原点が画像の左上で PIL と同じなのに、`rasterize()` が
`1 - v` を使っていた。**頭皮マスクが金髪の UV 島から外れ、髪色を移しても
最終レンダに何も反映されなかった。** 既知の頂点で裏を取って確定した:

| 頂点 | UV | 反転なし | 反転あり |
|---|---|---|---|
| 上唇 | (0.500, 0.404) | **[136, 44, 39] 唇の赤** | [190,140,109] 肌 |
| 頭頂 | (0.305, 0.033) | **[188,151,100] 金髪** | [ 80, 24, 6] 暗部 |
| 鼻先 | (0.500, 0.338) | [208,152,123] 肌 | [182,132,101] 肌 |

### 14.2 テクスチャのアルファを落として髪カードが板になった

`vrm/extract_texture.py` が `.convert("RGB")` していた。Rocketbox の `opacity` は
**RGBA で 78.3% が透明**。RGB に落として書き戻すとカードが不透明な板になり、
顔に被さって held-out ArcFace が **0.6548 → 0.5609** に落ちた。

### 14.3 ランドマークの `xyz` を変形後のモデルに使った

まつ毛の判定でテンプレートの `xyz`（身長 1.743m 基準）を、体型変形後のモデル
（1.60m・倍率 0.918）と比べていた。目の位置が 130mm ずれ、半径 30mm では
**1枚も拾えず「まつ毛 0件」**になった。`vertex` は頂点番号なのでトポロジ不変 ——
変形後のモデルから引き直す。

### 14.4 幾何の帯をそのまま服のマスクにした

帯は UV の島の一部しか覆わない。脚の帯（高さ 0.07〜0.60）はジーンズの島の
上半分だけを拾い、**腰まわりのデニムが別の島として青く残った**。帯を**種**にして
UV の連結成分へ広げるようにした（成分18個。シャツ→[5,12,13,16]、ズボン→[14,15]）。

### 14.5b Reinhard の外挿が色域外へ飛ぶ（襟が緑になった）

領域の中に元の分布から外れた画素があると、標準偏差合わせが外挿する。ブレザーの
襟元に覗くインナーの肌色がシャツのマスクに入っていて、**襟の中央が緑の斑**になった。
正規化偏差を ±2.5σ にクリップして止めた（`hair_color` と `garment_color` の両方）。

### 14.5 頭皮を幾何の高さだけで切ると額が暗くなる

眉の高さ（頭の 0.72）で切ると**額の肌まで頭皮に入り**、髪色を移すと額に暗い帯が
出た。生え際の高さはテンプレートの幾何からは分からない。正しい境界は
**投影が上書きしなかった領域**（焼いた結果と元の差が 3 以下）。被覆 19.2% → 12.7%。

## 16. アプローチの変更 — 髪は生成メッシュから切り出す

§13.2 で「Rocketbox に髪のボリュームが無いので色しか寄せられない」と結論したが、
**制約の置き方が間違っていた。**

ラップ方式は生成メッシュを「測るためだけ」に回して捨てている。捨てたものの中に
**本人の髪がジオメトリとして入っている**。そして——

**髪は固定トポロジを必要としない。** ラップが必要だったのは

  - 顔 … 表情モーフ175個が頂点番号で定義されている
  - 体 … 手塗りウェイトが頂点番号で定義されている

からで、髪に要るのは骨1本（将来はスプリングチェーン）だけ。
**固定トポロジの制約は顔と体にしか要らなかった。**

`blender/add_hair.py`。ラップが求めた相似変換（`wrap.json` の `align`）で生成メッシュを
テンプレート空間へ運び、アバター表面からの符号付き距離で髪を切り出して、
**別のスキンメッシュとして**載せる（結合しない ——シェイプキー175個を壊しうる）。

### 16.1 何がジオメトリで、何がテクスチャかを測って分けた

生成メッシュの頂点をアバター表面からの符号付き距離で見た:

| 領域 | 頂点 | 距離の分位(mm) 5/25/50/75/95 |
|---|---|---|
| 前（顔） | 205,683 | −47.7 / −11.8 / **+0.5** / +12.4 / +41.9 |
| 上（頭頂） | 163,673 | −47.3 / −11.7 / **−0.6** / +12.9 / +44.5 |
| 後 | 221,103 | −40.9 / −1.7 / **+13.4** / +28.1 / +56.1 |
| 側 | 175,085 | −46.5 / −3.6 / **+6.2** / +18.9 / +46.0 |

**頭頂では髪の表面が頭皮とほぼ一致していた**（上位15%の高さで中央値 −1.3mm、
外側は 44.5% だけ）。ラップ後の頭皮はテンプレート由来で、そこに髪が描いてあるぶん
元から髪の体積を持っているため。

→ **頭頂に足すべきジオメトリは無い。色だけ**（§13.2 の色転写が担う）
→ **ジオメトリが足すのは側頭と後頭部のシルエット**。テンプレートは髪を後ろで
   束ねた形なので、ボブのように張り出す髪型はここでしか表現できない

### 16.2 閾値は場所によって変える

単一の閾値では分けられない（`--outside` を掃引した実測）:

| 閾値 | 結果 |
|---|---|
| 8mm | 頭頂の髪は残るが**顔の表面まで全部残る** |
| 15mm | 顔がまだ残る |
| 25mm | 顔は消えるが**頭頂も禿げる** |

頭頂の髪は頭皮から 8〜15mm しか浮かないのに、顔の上の生成メッシュもラップの
残差ぶん数mm浮くので量的に重なる。**最近点の法線の向き**で分けた ——
顔の上（前向き）は 30mm、側頭・頭頂・後頭部は 8mm。

### 16.3 断片は「小ささ」ではなく「場所」で決まる

生成メッシュの髪は**7,753個の連結成分**に断片化しており、「大きい順に N 個」では
髪が取れない（上位8個でも細い筋しか残らなかった）。頬や肩に乗る粒は 800〜2000頂点
あって、下限を上げると髪の体積まで削れ左右非対称になった。

実体は**首の切り口の残骸**だった。髪を載せるのは体型変形の前なので、切り口が
0.918倍に縮んで肩の高さに来る。切る高さを顔マテリアルの下端ではなく
**頭の高さの比 0.30**（顎は約 0.38）にしたら消えた。

### 16.5 「粒」の正体は穴だった

頬と側頭に見えていた黒い粒は、拡大して初めて分かった ——
**髪メッシュに開いた穴から肌が透けていた**。距離の切り口が髪の内部を通り、
髪の表面が一時的に肌へ近づくところが虫食いになる。だから

| 試したこと | 結果 |
|---|---|
| 連結成分の下限を上げる | 粒は髪本体の一部なので落ちない。上げると髪の体積が削れて左右非対称に |
| 大きい順に N 個だけ残す | 髪は 7,753成分に断片化しており、上位8個でも細い筋しか残らない |
| 空間クラスタ（距離で塊にする） | 半径 1.5mm でも上位2塊に含まれたまま |
| 収縮→膨張（opening） | **穴は埋まらない。逆をやる必要がある** |
| **膨張→収縮（closing）** | **穴が埋まって塊になった** ← 採用（3回） |

closing を 5回以上にすると髪が頬へ張り出すので 3回。効果:

| | バスト tweed | 全身 tweed |
|---|---|---|
| closing 無し（`gw_007`） | 0.6669 | 0.6480 |
| **closing 3回（`gw_008`）** | **0.6814** | **0.6552** |

### 16.4 結果

| | バスト tweed | 全身 tweed | 頂点 |
|---|---|---|---|
| 接合 v2 | 0.6189 | 0.5329 | 129,458 |
| ラップ（テクスチャのみ・`gw_004`） | 0.6629 | 0.6470 | 5,569 |
| 髪ジオメトリ（粒あり・`gw_006`） | 0.6827 | 0.6580 | 36,666 |
| **髪ジオメトリ（`gw_007` 最終）** | **0.6669** | **0.6480** | **32,678** |

`gw_006` のほうが数値は高いが**肩に黒い粒が乗っている**。目視で `gw_007` を採る。
**指標だけで選ばないこと。**

モーフ175個・ポーズ検査・KEHAI 検査はすべて維持（結合していないため）。
KEHAI 登録名 `subject_a_hair`。

## 17. 髪を揺らす — VRM で書き出す（アドオンは使えなかった）

**プレーンな glb では KEHAI は髪を揺らせない。** KEHAI の
`frontend-src/src/renderer/src/utils/glb-humanoid.ts` が明記している:

    What such a model does NOT get, because the file cannot describe them:
    spring bones (hair/cloth physics), VRM expression presets, ...

KEHAI は `@pixiv/three-vrm` の `springBoneManager` を毎フレーム更新しているが、
それが作られるのは `VRMC_vrm` を持つ本物の VRM のときだけ。

### 17.1 骨を作る

`blender/add_hair.py --spring-joints 3 --spring-groups 3`。髪を頭の中心から見た
方位角で3束に分け、束ごとに z を等分してその高さの帯の重心をチェーンの節にする
（束が横に張り出していてもチェーンが芯を通る）。

**末端ノードを1つ余分に作る。** VRM の spring は `joints` の隣り合う2節で1区間を
作る（three-vrm は `joints[i+1]` を `joints[i]` の子として使う）ので、N本を
揺らすには N+1個の節が要る。実測: 末端が無いと 3節=2区間で、いちばん先の骨が動かない。

### 17.2 VRM アドオンは使えなかった

`blender/export_vrm.py`（VRM Add-on 4.5.0）は Rocketbox 由来のリグでは
**何も書き出さずに CANCELLED を返す**。原因を1つずつ潰したが、どれも本命ではなかった:

| 疑い | 結果 |
|---|---|
| 脚の別名（`leftUpperLeg←LeftLeg` の誤対応） | **本当のバグ。直した**が失敗は続く |
| `Icosphere`（未スキンのメッシュ） | 除去しても続く |
| ルートの scale 0.01 ＋ 回転 | 焼いても続く |
| 顔ボーン26本の名前 | `Face_` を付けても**探索回数が 80,686,221 で完全に同一** |
| 私が足した髪のボーン | **素のテンプレートでも同じように失敗する** |

    [VRM Add-on:WARNING] Structure search completed:
      Total searches: 80,686,221 (soft limit: 1,000,000)

しかもアドオンは独自に誤った対応を生成する（`hips←Spine`、
`leftUpperArm←LeftShoulder` と1つずれる）。残るのは階層の形そのもの。

**アドオンの自動推定に頼る必要は無い。** どのボーンがどの humanoid ボーンかは
こちらが知っている。`vrm/make_vrm.py` で `VRMC_vrm` を JSON で直接書く
（`vrm_finalize.py` が拡張を消すのと対称）。実測で humanoid 55本（指30本を含む）
が対応し、未対応 0。

**`export_vrm.py` の副産物として直したもの**（他のスタイルにも効く）:

- 脚の別名 —— Mixamo は `UpLeg` が腿・`Leg` が脛。別名表の `"leg"` を upperleg に
  入れていたので lowerLeg が空になっていた。KEHAI 側（`glb-humanoid.ts`）は
  最初から正しく分けている
- `export_scene.vrm` の**戻り値を見ていなかった**。アドオンは失敗しても例外を
  投げず `CANCELLED` を返すので、後段の `set_double_sided` が FileNotFoundError で
  落ちるまで気づけなかった
- マテリアル無しのメッシュ（`Icosphere`）の除去

### 17.3 結果

```
VRM 1.0   humanoid 55本   spring 3本 × 4節（= 3区間）
KEHAI 検査 合格   モーフ 175   まばたき・口パクとも認識
```

## 18. 服の構造 — 2つの方法を試して両方外した

色は転写できた（§13.4）が、**ブレザーの襟・前開き・中のインナー**という構造は
テンプレートに無い形なので色では入らない。

### 18.1 生成メッシュから服を切り出す（位置合わせで破綻）

髪と同じ手（`blender/add_garment.py`）。Tポーズ写真から TRELLIS で全身を生成すると
**赤いブレザーの襟・前開き・インナー・黒いスラックスまで写真通りに出る**（431.9秒）。
生成メッシュの服は色で明確に分かれるので（赤 [172,21,40] / 黒 [32,31,35] 対
肌 [205,151,137]）、テンプレートのときと違って色で切れる。

破綻したのは**位置合わせ**:

| 方法 | 結果 |
|---|---|
| MediaPipe の関節を逆投影して Umeyama | **残差 116.6mm**。逆投影は服の表面に当たり、骨の内部位置と数cm系統的にずれる |
| 外接箱を等方スケール | 腕幅が 0.814m 対 0.579m で 23cm はみ出し、袖が腕から浮く |
| 外接箱を軸ごとスケール | 奥行きが 1.723倍に伸びて形が壊れた（袖が肩の上の赤い筒になった） |

髪が成立したのはラップが高精度な相似変換を与えてくれたから。全身にはそれが無い。

### 18.2 写真を体テクスチャに投影する（滲んで退行）

顔と同じ手。`preprocessing/body_projection.py` で MediaPipe の33点から
部位ごとの区分アフィンを作り、写真をレンダに合わせて歪める。残差 0.61px で
整列し、**襟・前開き・インナーが絵として乗った**。

しかし:

- 背景付きの写真を投影すると、体のシルエットが写真と違うところに**写真の背景
  （灰色）が焼き付く**。背景除去済み（RGBA）を渡すよう直した
- 関節どうしで合わせると、写真の**ゆったりしたジャケットの外縁**がモデルの外へ
  落ち、内側のインナー（白）だけが胸に来る → 胸が白い面に赤い斜線
- 「写真のジャケット幅 / 肩幅」で横を補正（kx=1.343）→ **さらに悪化**。
  区分アフィンの Gaussian 混合が胴の内容を脚へ滲ませ、赤い襷が脚まで伸びた
- **レンダ側の輪郭は使えない**。アバターの腕は下に垂れているので胸や腰の高さで
  輪郭を測ると腕を拾う（レンダ幅 423/577/695 対 写真幅 233/249/294）

### 18.3 胴だけ投影する（採用）

滲みの原因は投影ではなく**私のワープ側**だった。`project_face.py` の投影は
カメラからの綺麗な写像で滲まない。滲んでいたのは部位ごとのアフィンを Gaussian で
混ぜた画像のほうで、胴の内容が脚の画素へ流れていた。

**服の構造は胴にしか無い。** 袖と裾は単色なので色転写で足りる。胴に限れば
混合そのものが要らない（`--torso-only`）。胴の多角形（肩と腰、肩幅の 12% 外へ
広げて羽根ぼかし）でマスクする。

    インナーの白・両側の赤・ボタンまで乗った。脚への滲みは無い。
    held-out ArcFace  バスト 0.6814 → 0.6813   全身 0.6544 → 0.6474

同一性はほぼ中立で見た目は明確に改善するので**既定で有効**にした
（`--no-body-projection` で切れる）。

## 19. 体型変形が骨を動かしていない（直したが戻した）

`shape_transfer` は POSITION accessor しか書き換えないので、**メッシュだけ変形して
スケルトンが取り残される**。実測（`jobs/gw_007`、身長 1.743m → 1.60m）:

    ノードの translation の総和   924.8770 → 924.8737   ← ほぼ不変
    メッシュの実測身長            1.7433m  → 1.5997m

骨の位置が約 8% ずれる。バインド姿勢は整合しているので静止時は正常に見え、だから
長いあいだ気づかなかったが、回転の支点がずれるのでポーズを付けると変形がわずかに誤る。

`move_joints()` を書いた。世界位置を変位場で動かし、ローカルの translation を解き直し、
**inverseBindMatrices も張り直す**（`jointMatrix = globalTransform * IBM` なので
ノードだけ動かすと静止姿勢で崩れる）。glTF のレベルでは正しく動いた:

    Head の骨   y=+1.5224 → +1.3972   （1.6m の体として妥当）
    LeftFoot    y=+0.0997 → +0.0915
    メッシュ     y[-0.0042,+1.5958] のまま不変

**しかし Blender の往復で壊れる。** インポータを通すと評価後のメッシュが
**1.5958m → 1.7214m に伸びる**（生の POSITION は 1.5958m のまま）。倍率 1.0787 は
体型変形の 0.91777 の逆数に近い。下流の `project_face.py` はこの評価後メッシュで
画角を決めて焼くので、顔が引き伸ばされて held-out ArcFace が **0.6814 → 0.3922**
に落ちた。IBM の並び（列優先）と符号は確認済みで、原因はまだ掴めていない。

**既定で切った**（`--joints` で有効化）。コードと実測値は残してある。

## 21. 肘と手首が壊れる — 骨のピボット補正（解決）

利用者からの報告:「体を動かすと肘とか肩がおかしくなる」。原因は §19 で記録した
**体型変形が骨を動かしていない**ことだった。

### 21.1 骨がどれだけずれていたか

骨の位置と、その周り 6cm のメッシュ頂点の重心との距離（`jobs/gw_013`）:

| 骨 | 補正なし | **補正あり** |
|---|---|---|
| LeftArm（肩） | 47.7mm | **11.1mm** |
| LeftForeArm（肘） | 46.5mm | **14.9mm** |
| LeftHand（手首） | — | 24.0mm |
| Head | 61.1mm | **33.6mm** |

### 21.2 Blender を通した後に掛ける

§19 で「Blender の往復で壊れる」と書いたが、原因が分かった ——
**Blender の glTF インポータはスキンメッシュのノード変換を適用する**（glTF 仕様は
無視すべきと定めている）。実測: メッシュオブジェクトの `matrix_world` に
ルートの scale 0.01 と位置 0.92329 が入り、ノードの translation を書き換えると
評価後のメッシュが 1.5958m → 1.7210m に伸びる。ルートを正規化しても
（`vrm/normalize_rig.py`）変わらなかった。

**Blender を通す工程を全部終えた最後に掛ければよい。** `shape_transfer --joints-only`
を足した（頂点を一切触らず、ノードの translation と inverseBindMatrices だけ書く）。
パイプラインでは検査のあと、glb と VRM の両方に掛ける。

代償: `pose_check`（Blender）は補正前のファイルに対して走る。補正の検証は
**KEHAI の実機**で行う（§21.3）。

### 21.3 KEHAI（three.js）で測った効果

`scripts/kehai_probe.py` で、**剛体であるべき部位**（その骨に 0.9 以上のウェイトを
持つ頂点）を曲げたときの頂点間距離の変化を測る。ここが歪む＝メッシュが裂けている。

| 骨 | 補正なし 平均/最大 | **補正あり 平均/最大** |
|---|---|---|
| 肩 leftUpperArm | 0 / 0 | 0 / 0 |
| **肘 leftLowerArm** | 0.703% / 17.371% | **0.458% / 10.775%** |
| 股 leftUpperLeg | 0.629% / 6.942% | 0.630% / 7.093% |
| **手首 leftHand** | 2.820% / **42.506%** | **0.697% / 10.878%** |

**手首が4倍、肘が38%改善。** 肩と股は元から剛体なので変わらない。

**指標を取り違えないこと。** 最初は「肘の周りの頂点間距離の変化」で測って
補正ありのほうが悪い（5.12% → 11.9%）と出た。あれは**正しい肘の曲げでも起きる
皮膚の変形**で、支点が正しいほど大きくなる。剛体であるべき部位だけを見るのが正しい。

### 21.4 副産物: `vrm/normalize_rig.py`

ルートノードの変換を子へ焼いて単位行列にする。Blender の問題は直らなかったが、
Rocketbox 由来の `Bip01`（scale 0.01・回転・子はセンチ単位）という素直でない
階層を正規化する道具として残す。世界変換は保存される（実測で完全一致）。

## 23. 服のジオメトリ — 3手目も失敗（原因は姿勢の違い）

§18.1 の失敗は「逆投影した**表面**点を**骨**の位置と比べた」ことだと考え、
両側を表面点にして解き直した（`align_generated_body.py` を surface-to-surface に）。
それでも残差 99.2mm。使う点を変えて測ると原因が出た:

| 使った点 | scale | RMS |
|---|---|---|
| 胴のみ（肩・腰 4点） | 1.6773 | **22.3mm** |
| 胴＋膝（6点） | 1.6055 | **21.7mm** |
| 胴＋足首（6点） | 1.7357 | 23.8mm |
| 全身12点（腕を含む） | 1.4157 | **99.2mm** |

**腕が壊していた。** アバターは腕が下がったA字、生成された全身はTポーズで、
姿勢が違う。相似変換では原理的に合わない。

胴＋膝（21.7mm）で合わせ、袖を除外して（`--max-x`）胴と脚の服だけ載せたが、
**それでも見た目はテクスチャ版より悪い**。緩い衣服は 21.7mm のずれでも縁が
合わず、赤い塊になる。

### 23.1 4手目: 合わせるのをやめて沿わせる（シュリンクラップ）

相似変換で置けないなら、体表面へ投影して外側にオフセットを置けば、体型が違っても
必ずフィットする（`add_garment.py --shrink`）。実際フィットした
（x[-0.795,+0.787] → x[-0.246,+0.243] と体の幅に収まる）。

**しかし構造が潰れた。** 襟・前開き・インナーが体に押し付けられて消え、
まだらな赤いシャツになる。**フィットと構造の保存が両立しない。**

### 23.1b 5手目: RBF の変形場で運ぶ（**配置は解けた**）

失敗の原因を整理すると、袖を除いた胴と脚では**姿勢は一致しており**、
残っていたのは体型（比率）の違いだった。相似変換はそれを吸収できない
（対応点8組で残差 34.2mm）。**RBF（phi(r)=r ＋ 一次多項式）なら吸収でき、
しかも投影と違って衣服と体の間隙が潰れない。**

`align_generated_body.py` が対応点そのものを出すようにし、
`add_garment.py --warp` で変形場として掛けた:

    RBF の変形場で運んだ（対応点 8組・残差 6.66e-16）
    アバター  x[-0.579,+0.579] z[-0.004,+1.596]
    服        x[-0.830,+0.818] z[-0.113,+1.601]

**服が体に正しく乗った。** 4手目までの「浮く・はみ出す・潰れる」は消えた。

途中で踏んだもの: `bbox()` が `bound_box` を読んでいた。あれはキャッシュで、
頂点を直接書き換えた直後は**変形前の値を返す**。頭の切り捨て閾値が
z>0.349（正しくは 1.361）で計算され、体の大半を捨てていた。頂点から直接
求めるように直した。

インナーの生成りも色の集合に足した（`[r,g,b,許容]` で色ごとに許容を変えられる）
—— 生成り [202,191,185] は肌 [205,164,138] と距離 54.3 しかなく、赤や黒と
同じ許容だと肌まで拾う。

### 23.2 結論 — 配置は解けたが構造が残らない

4手すべて失敗した:

| 手 | 何をした | なぜ駄目か |
|---|---|---|
| 外接箱（等方） | 身長で合わせる | 腕幅が 23cm はみ出す |
| 外接箱（軸ごと） | 軸ごとに合わせる | 奥行きが 1.72倍に伸びて形が壊れる |
| 関節・表面対応 | ランドマークで相似変換 | 姿勢が違い（A字 対 Tポーズ）RMS 99.2mm。胴だけなら 21.7mm だが、それでも縁が合わない |
| シュリンクラップ | 体に沿わせる | フィットするが襟・前開きが潰れる |
| **RBF の変形場** | 対応点8組で滑らかに運ぶ | **配置は解けた。**が、切り出したジオメトリに構造が残らない |

### 23.3 6手目: closing と削減の切り分け、シェルへの投影（構造は元から無い）

「切り出しでラペルが均される」という §23.2 の仮説を検証した。closing 3回/0回、
削減あり/なし（268,433頂点のまま）の3設定を並べると**見分けがつかない** ——
closing も削減も無実。抽出したシェルは TRELLIS 自身のテクスチャでも、拡大すると
ポケット付きのシャツになる（TRELLIS が近くで幻視している）。

最後に、RBF で正しく配置したシェルに写真を投影して（構造は写真から、
立体感はシェルから）も、見た目は変わらなかった。テクスチャ版（§18.3）が最良。

**結論: 構造は生成ジオメトリに元から入っていない。** 服の**構造**（襟・前開き・
インナー・ボタン）はテクスチャ版で出荷済み。ジオメトリで足せるのは**シルエット**
（体からの浮き）だけで、それには布シミュレーション（クロスフィッティング）が要る。
この道具立てでは到達できない。

**配置の問題は5手目で解けた**（RBF の変形場）。残る壁は別の場所にある ——
色で切り出したジオメトリは、形態学処理と削減（268,433 → 55,226頂点）を経ると
**ラペルと前開きが均されて、プラケットのあるシャツになる**。胴を拡大して
並べると差が明確:

    テクスチャ版   ラペル・前開き・生成りのインナー・ボタンまで出る
    ジオメトリ版   プラケットとポケットのあるシャツ。縁が裂けている

**テクスチャ版（§18.3）を採る。** 残る課題は位置合わせではなく、
**細い構造を保ったまま生成メッシュから衣服を切り出すこと**（現状の
色しきい値＋形態学＋COLLAPSE 削減では、ラペルのような薄い折り返しが消える）。

道具は使える状態で残してある —— `--warp` は配置の正解なので、切り出しを
改善できれば載せ替えられる。

道具は残してある: `blender/add_garment.py`（色での切り出し・シュリンクラップ・
ウェイト転送まで動く）、`preprocessing/align_generated_body.py`。

道具は残してある: `blender/add_garment.py`（色で切り出し・ウェイト転送まで動く）、
`preprocessing/align_generated_body.py`（surface-to-surface の相似変換）。

## 26. Blender だけが誤読する原因 — 同乗アニメーション（解決）

§21.2 で「Blender の glTF インポータがスキンメッシュのノード変換を適用する」と
推測したが、**誤りだった。** 原因は Rocketbox のテンプレートが FBX 由来の
アニメーションを持っていたこと:

    animations 1  channels 243  名前 ['Bip01|Take 001|BaseLayer']

**Blender はインポート時にこれを1フレーム目で適用**し、ノードの TRS を古い値で
上書きする。骨を動かした後だとキーフレームは無効なので、結果として
`oldWorld · IBM_new` になり、評価後のメッシュが 1.5958m → 1.7210m に伸びていた。
three.js（KEHAI）はアニメーションを自動再生しないので正しく出ていた。

切り分けで潰した候補（どれも違った）:

| 疑い | 結果 |
|---|---|
| スキンメッシュのノード変換 | 単位行列にしても 1.7210 のまま |
| ルートの scale 0.01・回転 | `normalize_rig.py` で焼いても 1.7210 のまま |
| IBM の並び（列優先）・符号 | ノード由来と IBM 由来の世界変換が完全一致（差 0.00000） |
| **同乗アニメーション** | **落としたら 1.5958 になった** ← 正解 |

`move_joints()` でアニメーションを落とすようにした（骨を動かした時点で無効なので、
残す理由が無い）。これで**骨補正をパイプラインの途中に戻せた** —— 以前は
Blender が誤読するので最後に掛けるしかなく、`pose_check` が補正前のファイルしか
検査できなかった。今は工程3（体型を寄せる）で骨も動かし、`pose_check` が
**補正後**を検査する。

| Subject A | 9.3mm | 18.0mm | 33.2mm |
| 別人・女性 | 14.3mm | 25.5mm | 41.0mm |
| 別人・男性 | **0.2mm** | 4.2mm | **7.0mm** |

  （7.0mm）より上にある。ほぼ全部捨てていた

held-out ArcFace **バスト 0.6818 / 全身 0.6576**（全身は過去最高）・

## 28. KEHAI でユーザーが見つけた5点（2026-09-10・解決）

`subject_a_v7`（`gw_018`）を KEHAI で動かしたユーザーの指摘: **肩の骨格がおかしい／
ジャケットの裾が透けて（はみ出て）いる／髪が透けて斑点になる／元のモデルの髪が
残っている／生成した髪に襟が混ざる（写真のジャケットが髪と同色）**。
5点とも原因が別々だった（登録後に §28.7〜28.9 の 3 点が続けて出た）。1つずつ切り分けて直し、`gw_029` を `subject_a_v10` として登録した（v9 は同名ファイルを何度も上書きしたのでブラウザのキャッシュを疑い、名前を変えた）。

### 28.1 肩 — 骨の移動から肩の鎖を外す

§21 の骨のピボット補正は肘と手首を直したが、**肩を潰した**。腕の支点をメッシュ断面の
中心へ 11cm 下げると、Rocketbox のウェイトは「支点は肩の頂部」という前提で塗られて
いるので肩の頂部ごと腕と一緒に回り、待機姿勢で肩が内側に落ちる。

4方式を同じ画角で並べた（`shoulder_4way.png`）:

| | 骨 | 肩 | 肘・手首（KEHAI 剛体歪み） |
|---|---|---|---|
| v3 | 全部据え置き | 正常 | 破綻（手首 42.5%） |
| v7 | 全部移動 | **潰れる** | 良（手首 10.9%） |
| **v8a** | **肩の鎖だけ据え置き** | **正常** | **良（肘 0.458% / 手首 0.697% — v7 と同一）** |
| v8b | 全部移動（再現） | 潰れる | 良 |

`shape_transfer --joints-exclude LeftShoulder,RightShoulder,LeftArm,RightArm` を既定にした。
肩を据え置いても肘・手首の数値は 1 桁も変わらない（`move_joints` の除外は局所平行移動を
再計算するだけで、除外した骨の子は動く）。

### 28.2 髪が透けて斑点 — `doubleSided` が VRM 経路で落ちていた

生成した髪は三角形スープで法線の向きが 51.7% しか外を向いていない（§7）。glb 経路では
`set_double_sided` で両面にしていたが、**`make_vrm.py`（VRM アドオンを迂回した JSON 手術）は
それを通らず** 髪マテリアルが片面のまま出ていた。裏向きの三角形が消えて斑点になる。
`make_vrm.py` と `compress_textures.py` の両方で全マテリアルを `doubleSided: true` にした
（`double_sided_set` を報告に残す）。ジャケットの裾の「透け」も同じ原因（体マテリアルも
片面だった）。

### 28.3 元のモデルの髪 — テンプレートは髪を2系統で持っていた

髪カードの alpha を 0 にしても（§13.3 の `hair_color --clear-mask`）、Blender の背面レンダに
**金髪のポニーテールが残った**。切り分け:

- 出荷した `opacity` テクスチャの alpha は 94.7% が 0、ポニーテールの UV 上には不透明画素が
  1つも無い → カードは消えている
- ポニーテールの頂点は **`head` マテリアル（不透明）側**にあった。頭蓋の後端 z=−0.159 に対し
  z=−0.236 まで、8cm はみ出す 100 頂点 × 2 の独立シェル

つまり Rocketbox 女性素体は「不透明な束（head）＋半透明の毛束カード（opacity）」の2系統で
髪を作っている。束はテクスチャでは消せない。`add_hair.py` に `strip_template_hair()` を足した:
head の面を連結成分に分け、**最大成分（頭蓋）より後ろにはみ出す副シェル**を落とす。
目・歯・舌も head の副シェルだが顔の前側にあるので該当せず、男性素体には該当シェルが無い。
bmesh の shape layer ごと消すのでモーフは 175 個のまま（`SR_21_Jaw_Open` 31.48mm・439頂点
→ 同値を確認）。除去は `template_hair_shells` として報告に残る。

### 28.4 襟足の金髪 — 頭皮マスクは眉より上しか見ていなかった

束を消しても背面には**襟足に金髪の帯**が残った。§13 の頭皮マスクは「眉より上 ∧ 投影が
届いていない ∧ 毛束の高周波」で、テンプレートの髪が側頭から襟足まで描かれている
（UV では顔の島の左右の縁）ことを見ていなかった。

色では分けられない: テンプレの金髪と肌は Lab で中央値 11.6 しか離れておらず、肌自身の
散らばり（90% 点 21）より小さい。幾何で分ける — **顎の輪郭の端（68点の 0/16、耳の前）
より 4cm 後ろの三角形**に限り、そこで「投影が届いていない ∧ 毛束の高周波」を襟足とする
（`--nape-margin 0.04`）。耳は輪郭点の 2〜3cm 後ろまで伸びるので 2cm では耳が入り、4cm で
外れた。歯・舌・眼球は最大連結成分に限って除き、首の肌の粒は 6,000 画素未満の成分を捨てる。
マスクは 15.2% → 23.3%。

### 28.5 生成した髪に襟が混ざる — 切る高さと色の採取範囲

写真のジャケットが髪と同色（黒）なので、TRELLIS の生成メッシュでは襟が髪と同じ塊になり、
`--cut-frac 0.30` では顎の下（0.38）より下まで残って肩の上に黒い板が乗った。
**0.40 に上げた**（ボブは顎の高さで終わる）。同時に `hair_color` の側方サンプリングを
顎（68点の 8）より上に限り、ジャケットの黒が髪色の推定に入らないようにした。

### 28.7 髪が黒い切り絵になる — 生成髪のテクスチャが真っ黒だった（v9 登録後に判明）

v9 を KEHAI で見たユーザーのスクリーンショットでは、髪が**陰影の無い真っ黒なシルエット**
だった。Blender のレンダでは黒髪らしく見えていたので気づかなかった。

最初は `metallicFactor` を疑った（TRELLIS の glb は factor を省略＝1.0）。しかし
metallicRoughness **テクスチャ**の B チャンネルが平均 3/255 なので実効値は 0.01 —
金属ではなかった。JSON で factor 0 / roughness 0.7 を当てると KEHAI で陰影は戻ったが、
それは roughness が 0.9→0.63 になって鏡面反射が出ただけ。

本当の原因は**アルベド**。髪メッシュが参照する画素（テクスチャの 6.1%）の Lab は
**L 平均 5.5（中央値 4.0、90% 点 11.2）**、RGB で (18,16,17)。写真の髪は L 24.3。
TRELLIS は髪を写真の 5 倍暗く焼く。どんな照明でも黒い切り絵になる。

直し（`gen_wrap_avatar.py` の新しい段）: 髪メッシュが使う UV の範囲を
`texture_processing/uv_mask.py` で取り、その画素だけ `hair_color`（Reinhard）で
写真の髪の統計に合わせる（`--min-luma 0`。既定の 6 だと中央値 4 の画素が対象から
外れる）。L 5.61 → 24.25（狙い 24.34）。毛束の陰影構造は残るので、Blender では
茶色の髪に毛流れが出る。生え際・耳まわりに肌の色がにじんだ画素（髪の分布から
13σ 外）は +2.5σ に切られて明るい斑になるので、`--outlier-sigma 4` で髪の平均色で塗る
（2,774 画素）。

あわせて `add_hair.py` で髪マテリアルの metallicRoughness テクスチャの結線を切り、
`metallicFactor 0 / roughness 0.7` の定数にした（テクスチャ 1 枚分軽くなる）。
`check_kehai_model.py` には**実効金属度**（factor × テクスチャ B の平均）が 0.5 以上の
マテリアルを不合格にする検査を足した。factor だけ見ると TRELLIS の glb を誤検出する。

### 28.8 髪色の標本が写真によって狂う — セグメンテーションに替えた

§28.7 の髪色合わせを別人 2 名で回すと、**暗い茶髪の女性が L 58 の金髪**になった。
`hair_color.hair_pixels` は「眉より上・顔の左右の帯・肌色から遠い画素」という幾何の
ヒューリスティックで髪を採っていて、背景が単色（Subject A の写真館）でしか当たらない。
街路の写真では木と空が帯に入る。短髪で額の広い男性では強く照らされた額と青い上着が
入り L 64 になった。帯を狭め、Lab の色相で額を落とす手も試したが男性は L 55 のまま。

`--debug-mask` で標本にした画素を塗って見ると一目で分かる（`hairmask_cmp.png`）。

替え: MediaPipe の多クラス人物セグメンテーション（`selfie_multiclass_256x256`、
髪＝クラス 1）を `preprocessing/hair_mask.py` にした（genesis-eval、16MB）。3 人とも
髪だけが取れる。写真は生の顔写真ではなく **rmbg 済みの頭の切り抜き**（`head_rgba.png`、
生成済みの頭を使い回すときはその頭を作ったジョブのもの）を渡す。標本の Lab L:
Subject A 11.0（生写真からの 24.3 は背景の灰色が混ざっていた）、女性 18.0、男性 55.6
（この人は実際に明るい茶髪）。`hair_color --photo-mask` でセグメンテーションを使い、
無ければ従来のヒューリスティックに落ちる。

### 28.9 髪が「あみあみ」— スープを穴の無い殻に作り直す

髪色を合わせて明るくなると、今度は**網目**が見えるとユーザー。出荷した髪メッシュを測ると
辺の **38.6% が境界辺**（167 の断片、最大でも 1,899 面）。TRELLIS のスープから頂点マスクで
切り出しているので穴だらけで、closing（§27）ではマスクの穴しか埋まらない。
両面描画で「透け」は消えたが、穴は網目として残っていた。

`add_hair.py` の `rebuild_shell()`: 切り出した頂点を点群にして半径 3mm の球で体積化
（Points to Volume）→ 等値面をメッシュ化（Volume to Mesh、voxel 1.5mm）→ 球の分だけ
法線方向に縮める → UV を元のスープの最寄り面から移す（毛流れのテクスチャはそのまま）。
スープ 72,067 頂点 → 殻 116,520 → 削減 19,991。**境界辺 0%・閉じた曲面 7 個**。
単位の罠: 髪は Bip01（0.01 倍）の子でローカル座標が cm なので、m 指定の半径を換算する
（最初は 0.04mm の球になって粒の雲が出た）。頭頂は殻がテンプレの頭蓋（髪の厚みを含む）の
内側に入るが、頭頂は頭皮マスクの髪色で見えているので問題ない。

球の分だけ縮めると、髪が薄い側頭で殻が頭蓋の内側に入り**肌（とくに耳）が髪を突き抜けて
斑**になった。テンプレの耳は本人の耳より外に突き出ているので、最近点の法線で押しても
中心からの放射で押しても耳の内側の面へ逃げて耳先が残った（両方試した）。採ったのは
**外側から内側へのレイキャスト**: 頭の重心から各頂点へ伸ばした半直線を head マテリアルの
面に外側から当て、最初に当たる面（その方向で一番外の皮膚＝耳なら耳先）より 3mm 外に
頂点を置く（`--shell-gap 0.003`、466 頂点）。首から下は head マテリアルでないので
毛先が肩に押し出されることはない。中心はボーンの `head_local` ではなく head 頂点の重心
（Bip01 の軸のせいでボーンからは 1.5m ずれた）。押し出しは**平滑化と削減の後**に掛ける
（平滑化は閉じた殻を縮め、削減は面を粗くするので、先に押しても耳がまた出た）。

もう1つ、切り出しの側: テンプレの耳は本人の耳より外に突き出ているので、写真で髪が
耳を覆っていても、その髪の点は「テンプレの耳の中」（符号付き距離が負）になって捨てられ、
髪に耳の穴が空く。68 点の顎の輪郭（0/16）と目尻（36/45）から耳の箱を作り、その中の
head の面を距離の表面から外す（`--landmarks`、178 面）。外側かつ首より上の点が
90,405 → 99,465 に増えた。なお Subject A の写真は向かって右の耳が髪の外に出ている
（髪を耳に掛けている）ので、その側で耳が見えるのは正しい。

殻の UV は元スープの最寄り面から来るので生え際の肌色がまだらに乗るが、
髪色合わせの外れ値塗り（`--outlier-sigma 2.5`）で消える。

半径 3mm では殻が **8 個の塊**に分かれ、塊の間の穴から背景が透けて KEHAI では依然
「あみあみ」に見えた。6mm と 8mm を並べ（`shell_radius_cmp.png`）、**8mm・voxel 2mm** を
既定にした。塊は 3 個になり穴が消える。球の分は法線方向に戻すので輪郭は膨らまない。

最終（`gw_029`、`subject_a_v10`）: 頂点 32,788・髪 19,998（閉じた殻、出荷 glb で境界辺 0%・
3 成分）・8.9MB・held-out ArcFace バスト 0.6764 / 全身 0.6714・KEHAI 剛体検査合格。
実行時間は 228→335 秒（殻の体積化と削減）。
